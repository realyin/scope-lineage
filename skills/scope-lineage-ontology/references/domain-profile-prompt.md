# 领域配置写作提示词（`domain-profile/1` 草稿）

你要从一份证据（`evidence.md`，由 `scope-lineage domain-profile evidence` 从语料数出来）写出这个数仓的领域配置草稿，
以及逐条理由。工具只报观察，不下结论；你只写证据撑得住的条目，撑不住的留给人确认。

## 你要写的两份文件

1. `domain-profile.draft.json`：`domain-profile/1` 格式的配置草稿。
2. `domain-profile.reasons.md`：逐条理由，分两节——`## 已写入` 和 `## 待确认`。

### `domain-profile/1` 的格式

```json
{
  "doc_format": "domain-profile/1",
  "qualifier_terms": ["运费"],
  "table_name_convention": {"incremental": ["inc"]},
  "concept_words": {
    "event": ["下单"],
    "entity": ["门店"],
    "summary": ["周报"],
    "measure_suffixes": ["销量"],
    "filter_words": ["已发货"]
  }
}
```

（例子是合成的零售词，只示范形状，不要照抄。）

- 只有这四个键；每个键都可省略；没有内容的键不写。不要加别的键，未知键是错误。
- `table_name_convention` 只有 `full`、`incremental` 两个子键，值是后缀列表：只含字母和数字、不写前面的 `_`。
- `concept_words` 只有 `event`、`entity`、`summary`、`measure_suffixes`、`filter_words` 五个子键。
- 每个列表都加在包内置的通用词之上，不替换它们。

### 理由文件的格式

每个条目（每个后缀、每个词）一行，键写完整路径，值和键各用一对反引号，后面跟冒号（全角、半角都行）：

```
## 已写入

- `table_name_convention.incremental` `inc`：带分区条件的读取全是范围读（12/12）。依据：evidence 后缀 inc
- `qualifier_terms` `运费`：多个金额列的注释写明「运费」口径。依据：shop.order_inc.freight_amt 的注释
- `concept_words.event` `下单`：表注释和表名都在说下单这件事。依据：表注释「门店下单流水」

## 待确认

- `table_name_convention.full` `snap`：倾向全量。单分区读为主（40/41），写入没有窗口筛选；需要人比较相邻两个分区的行数
- `qualifier_terms` `券后`：只在一列的注释里出现，拿不准是不是本数仓的口径
```

- **草稿里的每一个条目，在「已写入」都要有一行**，键路径和值与草稿一字不差（后缀不分大小写）。缺一行核对就不过。
- 「待确认」的条目**不写进草稿**。

## 规则

### 后缀（`table_name_convention`）

- 证据建议 `incremental` 的后缀：照建议写进 `incremental`，「已写入」里写出读法的计数。认为建议错了的，不写，列进「待确认」并写明原因。
- 证据标「待确认（倾向全量）」「待确认（无倾向）」或建议为「无」的后缀：**一律不写进草稿**，列进「待确认」，写明倾向和要人判断的地方。
  只看读法分不出「每个分区一份全量」和「每天只取当天那一批增量」，所以工具从不直接建议 `full`，你也不写 `full`。
- 证据里合并成一行的小后缀、只写不读的后缀：多半是表名里的普通单词，不写，也不用列。
- 证据开头写了元数据覆盖率不足、不给建议的：后缀一个都不写。

### 修饰词（`qualifier_terms`）与概念词（`concept_words`）

- 只写在证据材料（第二、三部分）里出现过、确实是本数仓业务口径的词。不编造证据里没有的词。
- 第四部分「已内置的通用词」已经有的不写。
- 每个词的理由里写出依据：哪条注释（写出处，例如 `库.表.列` 的注释）、哪个表名词元。
- 各键的意思（下游怎么用它）：
  - `qualifier_terms`：口径限定词。表语义校验第 12 项用它找「输入列的注释带了限定、目标表没写」的情况。中文词要成词才算命中（「运费」能在「运费金额」里命中，「运」不能），拉丁字母按整词、不分大小写。写在度量列注释里、会改变数字口径的词才写（含不含某种费用、是否测试数据……）。范围限定（只算某个地域、某个时间段）、注释里字面写着「口径」的说法、本数仓特有的计算规则（例如会不会重复计算），都算口径修饰。一个词只出现在一张表上，不是不写的理由：只要它改变那个数的口径，就写。
  - `concept_words.event` / `entity` / `summary`：概念层判断一张表是事件、实体还是汇总时的词票。中文按子串，拉丁字母按整词、不分大小写。概念层只看**表名和表注释**投票，所以依据只能是表名词元和表注释；只在键列注释里出现的词投不出票，不写。
    写之前先数一遍：这个词命中了哪些表（表名里有这个词元，或表注释里有这个词）。按下面的顺序判断：
    1. 命中的表里，多数确实是这一种（事件表、实体表、汇总表），才写进草稿；理由里写出命中几张、其中几张是这一种。
    2. 命中的表里，多数是别的种类（例如一个「实体」词主要出现在报表、汇总表或流程表上）：写进去会给这些表投错票，**不写，也不列进「待确认」**。
    3. 这一种的那几张表已经被内置词命中，新词只会多命中别的表：等于只添错票，**不写，也不列**。
    4. 只有两种情况列进「待确认」：命中的表里这一种接近一半、多一张少一张就翻转；或者这些表到底算哪一种，本身要懂业务的人来定。
    同一个标准适用于每个词。一个词在种类键下不合适时，再看它是不是更像一个切片（版本、副本、下钻层级、状态），是的话按 `filter_words` 再判一次。
  - `concept_words.measure_suffixes`：名字以它结尾时，说明这是一个度量（例如「…销量」），不是概念本身。名字候选来自表注释和键列注释，所以要有某条表注释或键列注释以它结尾。
  - `concept_words.filter_words`：名字里带它时，说明这是概念的一个切片（例如「已发货订单」），不是概念本身。要有某条表注释或键列注释包含它。同一组的词（例如几个状态词、几个版本词）要么一起写，要么一起列进「待确认」，不要只写其中一个。
- 拿不准的词列进「待确认」，不写进草稿。宁可少写：多写一个不是本数仓口径的词，下游每张表都会被它误读。

### 不得做的事

- **不得写 `confirmed.json`**，也不得在理由里声称「已经过人工确认」。确认只由人做，编排者照人的答复写确认文件。
- 不要改 `evidence.json`、`evidence.md`。
- 不要读证据以外的语料、任务 SQL 或别的运行目录来「补充」词。

## 写完后自检

自检命令是 `domain-profile check`（不带 `--confirmed`），完整写法见派你来的说明。

- `exit=0`：通过（可以有 `hint:` 行；`hint` 指出的「证据建议了 incremental、草稿里没写」要么补上，要么在「待确认」里写明原因）。
- `exit=1`：按 `error:` 行逐条改。「没有依据」的条目删掉或挪进「待确认」；「缺理由」的补一行。不要为了通过去改证据。
