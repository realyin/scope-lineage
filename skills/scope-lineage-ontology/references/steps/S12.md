## S12 确认回写（可选）

**目的**：把 owner 对页面「待确认问题」的回答写回文档，下一次渲染带 ✓。确认行粒度、列含义或码值的表再派一轮修订，
把正文改得与确认一致。

**前提检查**：owner 的回答已拿到。列出每张表的问题：每行前面是状态，后面是一条确认的开头（`table`、`target`、`asked`），
`asked` 是问题原文，整段复制进确认文件再补 `value`、`by`、`date`：

```bash
python3 -c 'import json,sys
for p in sys.argv[1:]:
    d = json.load(open(p))
    for q in d["summary"].get("questions", []):
        print(q.get("status"), json.dumps({"table": d["table"], "target": "question:" + q["id"], "asked": q["text"]}, ensure_ascii=False))' "$RUN"/docs/*.json
```

**命令**：用 Write 工具写 `$RUN/confirmations/<日期>.json`（`semantic-confirmations/1`），每条一个回答：

```json
{
  "doc_format": "semantic-confirmations/1",
  "confirmations": [
    {"table": "demo_dwd.dwd_party_customer_info_df", "target": "question:q1",
     "asked": "性别码值除了 F、M、U 以外，还会不会出现其他值？",
     "value": "不会。注册系统只允许 F、M、U 三个值。", "by": "demo-reviewer", "date": "2026-01-01"}
  ]
}
```

`target` 有七种写法：`question:<id>`（id 是上面列出的，例如 `q1`，不能只写 `question:`）、`column:<列>.meaning`、
`column:<列>.code_values`、`summary.row`，以及平台查询的三种观测（见下面「观测条目」）`summary.row.observed`、
`column:<列>.observed_values`、`input:<库.表>`。**每条 `question:` 都要带 `asked`**（上面列出的问题原文，一字不改）：重写会给问题
重新编号，运行中的重放都带 `--require-asked`，没有 `asked` 的回答一律 unmatched，`FACTS` 里也不出现。owner 若在浏览页上回答（服务以 `--answers` 启动），页面「导出确认文件」下载的文件
（或 `scope-lineage-service answers export` 写出的文件）就是这种格式（已带 `asked`），可以原样放到 `$RUN/confirmations/` 交给下面的 `semantic confirm`，不用手写。
页面上的**结构化回答**（行粒度、列含义、码值）导出成结构化条目在前（每个码值一条单对象条目，不用列表）、关掉问题的 `question:` 条目在后；
结构化条目不带 `asked`。放进目录时文件名要排在旧文件之后（导出文件名带上日期时间，例如 `page-20261124-1530.json`）：目录按文件名顺序重放，后面的覆盖前面的。
导出时页面「导出前请看」（或命令 stderr 的 `note:` 行）提到某个码值的含义被改了：重放只合并、不撤回，先把 `$RUN/confirmations/` 里确认旧含义的那条删掉，再放新文件。
页面没有材料包，`semantic confirm` 也没有：常量列上的码值、SQL 不会写出的空串码值照样写进文档，到 S9 校验才以「确认与 SQL 矛盾，交回 owner」失败，按下表处理。
**观测条目**（平台查询的结果，同样是确认条目，放进同一个目录）：观测不是定义，只说明查询读的那几个分区、那一天。
每条的 `value` 都带 `query`（查询标识）、`on`（执行日期 `YYYY-MM-DD`）、`rows`（观测范围内的行数，至少 1）、`partition`
（`{"column": "dt", "values": ["20261119"]}`，范围写 `from` / `to` / `count`，不分区写 `{"column": null}`），可选 `requested`
（原定批次日，回退到最近可用分区时写）、`filter`（查询的前置条件，即本表任务自己的读取条件）、`engine`；`by` 是核对并确认这条结果的人。
贴回的结果按交回格式（`sql_id, status, run_on, bizdate, sql_executed, columns, rows, note`）这样落成条目，目前手写，没有解析命令：

| 查询形状 | 落到 | 怎么填 |
| --- | --- | --- |
| 按键计数（输出 `rows, keys, duplicate_keys`） | 本表行：`summary.row.observed`；输入表：记在**读它的目标表**名下的 `input:<库.表>` | `sql_id` → `query`，`run_on` → `on`，`bizdate` → `partition.values`（与原定日不同时原定日写 `requested`）；`grain_columns`（本表行）或 `columns`（输入表）写查询实际计数的列；`unique` 在 `duplicate_keys` 为 0 时写 `yes`，否则 `no`；`within` 写 `each_partition`（多分区分别计数）或 `all_observed`；照抄 `keys`、`duplicate_keys` |
| 取值清单（输出 `value, cnt`，`LIMIT 51`） | `column:<列>.observed_values` | 同上填依据；`values` 是 `{value, count}`，至多 50 个；返回 51 行时只写前 50 个并写 `complete: false`，否则 `complete: true`；被问到、计数为 0 的值写 `absent`；查询读的是来源列时写 `observed_on: <库.表.列>`（必须是该列的来源列之一）；标识类列只写计数，不写取值 |

`status` 不是成功、或行数为 0 的结果不写条目；其余形状（条件计数等）只作回答依据，不写观测条目。一条观测只记在发起查询的那张目标表
名下，不抄给别的表：别的表要用，按那张表的读取条件重查。写错的条目在 `semantic confirm` 的 `unmatched:` 行里报原因。

确认文件一直留在 `$RUN/confirmations/`，不删不改：从此每次写作、修订之后都重放整个目录（S4、S5、T4），
写作、审读、修订的提示词都带上它生成的 `FACTS`。然后（`--confirmations` 给整个目录，已经套用过的确认重放不改任何东西）：

```bash
sl semantic confirm "$RUN/docs" --confirmations "$RUN/confirmations" --reviews "$RUN/reviews" --require-asked; echo "exit=$?"
load_tables
sl semantic status "$RUN" --pages "$SEMPAGES" --only "${TABLES[@]}"
```

**产出与自检**：`Applied N confirmation(s) to M table(s) (unmatched=K)`（可能带 `, skipped=S`，见下表）。重放的是整个目录：
这次加的条目都不能在 `unmatched:` 行里；表重写过时，以前文件里的 `question:` 条目会 `question was rewritten`，这是正常的。之后每张被改的表一行：

- 只答了问题（`question:` 目标）的表：`<表>  fixed_doc_digest …`（回执移到了确认后的文档上），显示 `fixed render_stale`；
- 确认改了行粒度（`summary.row`）、列含义（`column:<列>.meaning`）或码值（`column:<列>.code_values`）的表，以及写进观测
  （三种观测目标同属结构化确认）的表：
  `<表>  fix record not carried: <目标> changed; …`，显示 `reviewed fix_unconfirmed`（审读没有高、中级发现的表是 `valid review_stale`）。
  这些表各派一轮 T4（S7 核对模式，带 FACTS）：结构化字段已由工具写好，修订者只把正文（一行是什么、要注意、问题、取数说明）改得与确认一致，
  收尾时重放确认再写回执。之后照常 S7 存修订记录、S8。

不要加 `--out`（`--out` 与 `--reviews` 同给退出 2，且就地确认才会移回执）。
在账本给这些表记一笔「确认回写」，并注明改没改结构化字段。只答问题的表不派修订，这一步不往 `fixlog.txt` 里追加；以后重写时修正点清单按「没有修订记录」处理（S4）。

**常见失败与处理**

| 现象 | 退出码 | 处理 |
| --- | --- | --- |
| 这次加的确认文件里有条目 `unmatched` | 0 | 逐条把原因告诉 owner（表名、问题 id 或列名写错），改确认文件后重跑；不要默默丢掉 |
| 以前的确认文件里的 `question:` 条目 unmatched，原因是 `question was rewritten`，这张表之后重写过 | 0 | 正常：重写换了问题，旧回答已通过 FACTS 交给写作者。记进账本，不回去找 owner |
| unmatched 原因以 `no asked` 开头 | 0 | 这条 `question:` 没带 `asked`：照前提检查列出的原文补上 `asked` 重跑；不要去掉 `--require-asked` |
| 这次加的条目 unmatched，原因是 `question was rewritten` | 0 | 导出之后问题被改写过，这条回答答的是旧问题：告诉 owner 问题现在的原文，请 owner 在页面上重新回答；不要改 `asked` 硬套 |
| unmatched 原因是 `question already answered differently` | 0 | 文档里这个问题已有别的回答：把两个回答都给 owner 看，由 owner 决定；owner 确认要改，才在这条上加 `"replace": true` 重跑 |
| 页面结构化回答的 `question:` 条目 `question was rewritten`，同一记录的结构化条目却已套上（码值、含义或行粒度改了） | 0 | 重放不把两条当一体：告诉 owner 问题现在的原文，请 owner 在页面上重新回答；结构化槽位若不该改，把这条结构化条目从确认文件删掉后重跑 |
| S9 校验报码值「确认与 SQL 矛盾，交回 owner」（页面回答的码值落在常量列上，或是 SQL 不会写出的空串） | 0 | 交回 owner：把 SQL 实际写出的值给 owner 看，由 owner 改回答；不要自行改确认或文档 |
| 摘要行带 `skipped=S` | 0 | 正常：这些回答文档里已经一字不差地有了（同一文件跑了第二次），什么都没改 |
| 确认文件格式不对，或同时给了 `--out` 和 `--reviews` | 2 | 对照上面的 JSON 改；去掉 `--out` |
| 只答了问题的表显示 `reviewed fix_unconfirmed` 或 `valid review_stale`，没有 `fixed_doc_digest` 那一行 | 0 | 工具早于 0.8.0。跑 `sl semantic fixed "$RUN" --only <这些表>`，应变成 `fixed render_stale`；不要派修订或审读 |
| 改了结构化字段的表显示 `fixed render_stale`（打印了 `fixed_doc_digest`，没有 `not carried`） | 0 | 工具早于这条规则：照样派一轮 T4（S7 核对模式，带 FACTS），T4 收尾会重新写回执 |
| 改了结构化字段的表，T4 回报后还是 `reviewed fix_unconfirmed` | 0 | 按 S7 的失败表处理；修订次数照算（S8 第 5 条） |

**完成判据**：这次加的确认条目没有一条出现在 `unmatched:` 行里（以前文件的 `question:` 条目在重写后 `question was rewritten` 是正常的，见上表）；只答问题的表是 `fixed render_stale`；改了结构化字段的表做完那一轮 T4，也是 `fixed`。

**下一步**：改了结构化字段的表先去 S7（T4 核对模式）；然后回 S9（全量校验与渲染），有目录时再做 S10g；目录里 owner 确认的条目按 S10f 改。
