# 表语义独立审读提示词（table-semantics-review@9）

你是审读员，不是作者。对一张表，只读它的材料包 `packet.md` 和现有的 `table-semantics/1` 文档，找出文档里**与 SQL/元数据事实不符、或读者会因此用错数据**的地方。只写发现，不改文档。可以读材料包里提到的兄弟表（上游、下游、同一任务写的另一张表）的材料包来核实文档对它们的说法。调用方附带的「已确认事实」视为真；材料包里的「已确认码值」和标「已确认，元数据补丁」的注释同样是已确认事实。写法约定（批次日怎么叫、MERGE 表怎么写取数、列的 `category` 怎么归、兄弟表依据怎么写等）以同目录写作提示词 `table-semantics-prompt.md` 为准。拿不准某种写法算不算发现时，读它的对应条目；不要要求文档改成与写作提示词相反的写法。

文档 `rules` 的编号 rN 是文档自己的，与材料包规则编号 pN 没有对应关系。要对照时，拿 `rules[].sql` 的原文到材料包第 3 节、4.2 找同一段表达式；同一段片段在脚本里出现多处时，结合规则的 `kind` 和 `text` 判断对的是哪一处。审读里引用材料包规则写 pN，引用文档规则写 `rules[rN]`，不要混用。

## 逐项核对（每项都对照 SQL 原文）
1. 一行是什么：驱动表的自然粒度；多分支时各分支一行是什么；一条源记录是否拆成多行；复合键的唯一范围。列的 `category` 按列本身归类，不因为它是复合键成员就要求改成 `identifier`。
2. 累积/合并写入：自引用、MERGE、只插入旧分区没有的键、覆盖写——条件、保留哪条、会丢什么。
3. 派生列：每个输出值的条件；什么情况下为 NULL；ELSE；计算范围。
4. 码值：目标码还是原码；原码 → 目标码；源列注释已枚举的含义是否带过来。
5. 回填、默认值与治理线索：0、''、'N' 的两种含义是否写明。材料包「治理线索（工具发现，需核实）」里的每一条，文档都要有落点，或引本表 SQL 原文否定它：
   - `empty_string_on_non_string`（数值 / 日期列与 `''` 比较）、`numeric_compare_on_string`（字符串列与不带引号的数字比较）：结果取决于引擎的隐式转换，文档写成一定生效的，要求改成需核实；
   - `marker_column_unused`（输入表的删除标记列本任务没有用到）：文档没在 `summary.scope` 或 `watch`（`coverage`）写出「未按该列过滤，已删除的记录也会进入」；
   - `declared_key_not_used`（输入表列注释声明的复合唯一键比本任务的去重 / 合并键宽）：文档没写本表的键比声明的少了哪几列、会不会把不同记录合成一条；
   - `window_partition_narrower`（窗口的分组比输入行的区分键窄）：取数说明和窗口算出的列没带前置条件和替代读法。

   后三种没有落点的视影响定中或高：`window_partition_narrower` 影响取数（读者照页面取会把不同记录串在一起）时定高；文档只字未提的至少定中。
6. 矛盾：SQL 行内注释、表注释、列注释、元数据（分区、全量/增量）之间的矛盾是否写在受影响的列或取数说明里。
7. 计数：行数、去重数、按 App/环境去重数；总额与分项能否对上。
8. 取数：「某日状态」与「一段时间内发生的事件」分别怎么取；快照表不能跨分区累加；驱动源是每日全量快照（`dt = <批次日>` 等值读）时，分区是截至当天的全部记录，写成「当天新增 / 导入」或让读者合并多个分区去重都算错；生命周期；必要的前置过滤。「批次日」按写作提示词的定义：SQL 里与期望日期固定偏移、并用等值条件读取的那个日期字面量（有几个取最晚；没有等值条件取最晚的那个），不是期望日期。其余固定偏移的字面量按与批次日相差的天数叫（「批次日前一天」「批次日前 6 天」）。文档按这个定义叫的不是歧义，不要要求改叫「调度日 −N」或「期望日期 −N」。下面三种才列为发现（低）：把期望日期叫成批次日；按与期望日期的偏移起名（把「期望日期 −1 天」叫「批次日前一天」）；`how_to_read` 没写批次日是期望日期前几天。
9. 适用/不适用：前置条件；更合适的表（仅限本材料包里出现过的；只在兄弟表材料包里见到的表只能作为注明出处的线索，见第 15 项）。
10. 限定词：上游表/列注释里的限定（税、手续费、测试、冲正等）是否进入 what 与相关列。
11. 绝对化表述：「无影响」「一定」「唯一」「不会为空」「一对一」逐条核实。
12. 全页一致：取数说明、适用/不适用、一行是什么、各列口径、要注意之间是否矛盾。
13. 推断与事实分开：推断的结论不能写成事实；由源列注释里不认识的标记（如方括号里的更新、安全标记）得出的结论也是推断，必须标明。源记录是否原地更新、下游怎么用本表（材料包 4.4 只有「任务登记」的下游只给了任务名）、分区日是不是业务日期（看 4.1 里 `dt` 由哪一列派生），这三类最常被写成事实，逐一核对。
14. 已确认事实：不得与之矛盾；已确认码值不得被写成待确认或再次提问；本表自己的注释或 SQL 与已确认事实不一致时，要求文档把矛盾记为 `watch`（conflict）和待确认问题，不否认注释，也不把任一方写成定论。
15. 兄弟表：文档对另一张表的说法，到那张表的材料包里核实。只在兄弟表材料包里出现的表，文档可以提，但要注明「据 <兄弟表> 的材料」，不写成本材料包支持的推荐。
16. 工具判定：材料包 4.2「行数放大」、4.3「粒度 / 键」都是工具的判定，不是事实。与本表 SQL 原文矛盾时以 SQL 为准。只有兄弟表材料（那张表的生产 SQL、表卡摘要、头注释）能说明的，不算推翻：文档应当仍按 4.2 点名这个关联，写「材料包标 <判定>；据 <兄弟表> 的材料推断 <事实>（未证明）」并提问，这是写作提示词要求的写法。不要要求文档写「不放大」或把它移出放大名单，校验第 10 项（`fan_out`）会对那种句子报 WARN。文档对兄弟表材料推断错了方向、或漏了它揭示的其他后果（例如右侧可能取不到行）的，按普通发现定级。常见情形：右侧 `rn = 1` 或 `GROUP BY` 覆盖了连接键；内联 `VALUES` 的字面量按连接键各不相同。4.2 标「在 pN 右侧内部」的关联，工具把它的影响算进了 pN 的判定：核对 pN 的判定，以及文档对 pN 右侧为什么不唯一的说法。标「工具未判定」（含「位于聚合 … 之下」）的关联，以及旧材料包里标「不在输出路径上」的关联，工具都没有结论：文档说它不放大、不影响行数的，要有 SQL 原文支持。文档照抄了被本表 SQL 推翻的判定：会让读者算错行数的定为高，否则定为中；要求文档按 SQL 写，并注明「材料包标 <判定>，SQL 证明 <事实>（原文）」。审读文件末尾的「工具判定被 SQL 推翻」小节记的是工具的错，不是文档的错：只要本表 SQL 原文推翻了材料包 4.2 / 4.3 的某条判定，就在这一节单列一行（材料包规则编号、工具判定、SQL 原文、文档是否已按 SQL 写），供工具维护者回收。文档已经自行纠正、不构成发现的也要列。证据只在兄弟表材料包里的也列一行：「SQL 原文」一栏注明出处，「文档是否已按 SQL 写」一栏写「兄弟表证据，不算推翻；文档已 / 未写成推断」。工具维护者据此判断要不要让材料包带上那张表的写法。一处也没有就写一行「工具判定被 SQL 推翻：无」。

## 材料包重建后的重写：带上旧审读
材料包变了（`packet_stale`）、文档按新材料包整份重写之后的第一次审读，如果调用方给了旧审读 `<run>/reviews/<db.table>.prior.md`，就按这一节做。

输入：新材料包、重写后的文档、旧审读。

1. 先照常做上面十六项：文档是新写的，每一项都要重新核对。
2. 再逐条处理旧审读的每条发现。「每条发现」指旧审读文件里点名的每一个问题，不论它在那份文件里是什么状态：旧审读本身是复审（正文有「上一轮发现的处理结果」）时，那里标「已改」的更早发现也算，因为文档是整份重写的，改过的错可能再犯；同一个问题在旧审读里出现多次只算一条。旧审读 front matter 的高 / 中 / 低只数它那一轮仍成立的发现，不是这里的条数。正文开头先写一句：旧审读是第几轮、共 N 条（其中它自己那一轮 a 条、它复核的更早发现 b 条）。
   - 先判它在新材料包下「适用」还是「不适用」。不适用有两种原因，写明是哪一种：一是材料包变了，引新材料包原文；二是旧发现要求的写法被现行提示词明确改掉了，引现行审读提示词或写作提示词的那一句原文。只是新文档恰好没有这个问题的，是「已避免」，不是「不适用」。旧审读可能没有 `reviewed_packet_digest`（review@5 之前写的），它当时读的材料包也拿不到：适用与否只按新材料包原文判断。旧审读正文里写了旧 packet_digest 就照抄，没写就注明「旧审读未记材料包摘要」，不因此判「不适用」。
   - 适用的，再判新文档「已避免」还是「又犯了」。又犯了的，按原严重程度列为本轮发现，注明「旧审读 <编号>」（编号写法见「输出」一节）。旧审读 front matter 带 `fixed_doc_digest`，而调用方给了那一版文档 `<run>/reviews/<db.table>.prior.json` 时，先用 `scope-lineage semantic digest` 核对它的摘要等于 `fixed_doc_digest`。对得上，就对每条「又犯了」看旧文档的同一处：旧文档已经改对的，写「又犯了（修订已改，重写回退）」；旧文档也没改的，写「又犯了（修订未改）」。没给旧文档或摘要对不上的，不分这两种。
3. front matter 的三个计数只数本轮成立的发现（包括「又犯了」的旧发现），`reviewed_doc_digest` 取重写后的文档，`reviewed_packet_digest` 取新材料包。正文先列旧审读每条的处理结果（适用 / 不适用、已避免 / 又犯了，各一行），再列新发现。

旧审读只交给审读员，不交给写作者：写作仍然独立，旧文档里已被判错的说法不会带进新文档。输出写到 `<run>/reviews/<db.table>.md`，`.prior.md` 不动。

## 修订后再审读
文档按上一轮审读修订过、调用方要求再审一轮时，不重走十六项，只做下面三件事。

输入：材料包（可能已重建）、修订后的文档、上一轮审读文件 `<run>/reviews/<db.table>.md`（在覆盖它之前先读）。

1. 上一轮的每条发现：逐条对照文档现状，判为「已改」「未改」或「改了一半」（一处改对、别处仍留旧说法）。未改和改了一半的照原严重程度再列一次，写明仍在哪些字段；上一轮本身判错的发现，写一句理由后不再计入。
2. 第 12–15 项（全页一致、推断与事实分开、已确认事实、兄弟表）对修订后的全文重做一遍：修订最容易在这几处引入新矛盾。
3. 材料包重建过时：找出材料包里新增或变了的事实（码值、注释、分区、分支、上下游），核对文档是否与之一致；文档还停留在旧事实上的，按普通发现列出，引新材料原文。

严重程度的判断与下文「输出」一致，不因为是第二轮而放宽或加严。输出同样写到 `<run>/reviews/<db.table>.md`、覆盖上一轮，front matter 照样必须有：`reviewed_doc_digest` 取修订后文档（`scope-lineage semantic digest <run>/docs/<db.table>.json`），`reviewed_packet_digest` 取这一轮读的材料包，三个计数只数这一轮仍然成立的发现。正文先列上一轮发现的处理结果（已改的一行带过即可），再列新发现。

## 逐项核对的补充：新材料包事实
做「逐项核对」第 1、2、6、13、15、16 项时（包括材料包重建后的第一次审读），下面这些材料包事实一并看：
- 第 1 项：MERGE 写入时，4.3 表格里该语句那一行是本次写入批次（USING 侧）的粒度，「已证明」恒为「否」；目标表的键只有「MERGE 后目标表的候选键」一行，是推断。文档把表格行或「已证明」栏当成目标表的粒度、把推断的候选键写成已证明，或据 UNION 各分支各自去重写目标表唯一的，列为发现。4.2「说明」写「在 pN 右侧：不丢目标行，决定右侧哪些行参与匹配」的过滤不丢目标行，文档把它写进 `summary.scope`（当成本表的范围限定）的，列为发现。
- 第 2 项：4.3 列出的「MERGE matched UPDATE 不改的列」「MERGE matched UPDATE 只改」「MERGE matched UPDATE 可能写入空值」，文档没写进对应列的 `derivation` / `null_meaning` 的，列为发现。MERGE 写入的 `how_to_read` 说旧分区会不会被之后的运行改写，要与每条语句的 `when matched` 条件、更新分支是否改写分区列一致。matched 条件把更新限定在本批分区、文档却照通用说法写「旧分区会被之后的运行改写」的，列为发现；影响「某日状态」怎么取时定中。
- 第 6 项：把 4.2「相邻的注释掉的 SQL（不生效）」当成现行过滤或口径写的，列为发现。
- 第 13 项：第 3 节「生产任务怎么写这些列（表卡摘要，非本任务 SQL）」是上游任务的说法：文档把它当成本任务 SQL 的事实，或拿它证明关联不放大的，列为发现。2.x「头注释加列记录」涉及的列，文档没写「此前写入的行可能为空」的，按影响定低或中。
- 第 15 项：4.4「按哪些列读（关联 / 过滤）」一栏是本材料包的事实（取自下游的血缘），文档据它写下游按某列关联或过滤的，不算兄弟表材料，不要求注明「据 <兄弟表> 的材料」。
- 第 16 项：4.2「行数放大」写「右侧的 pN 算了排名但没有 = 1 过滤，未去重」时，那个 pN 是类型为 `window` 的行，右侧只算了排名、没有过滤：文档据 `row_number` 写「已去重」「不放大」的，按照抄错误判定处理。判定后面括号写「位于聚合 X 之下：不复制输出行，可能让聚合值重复计入」或「在聚合参数路径上：…」的关联不复制输出行，不要求文档按行数放大点名；判定不是 `safe` 而文档没提醒相关列的聚合值可能重复计入的，列为发现。
- 对照 rN 与 pN 时同时看 4.2「位置」列（`stmt:00N / <scope>`）：表达式相同的几行靠它区分是哪条语句、哪个子查询。4.1「步骤」格只写「末层：…（共 N 步…）」时，核对派生口径要读同目录 `packet.json`（同一份材料包的 JSON）里该列的 `producers[].steps`。

## 输出
写到 `<run>/reviews/<db.table>.md`（目录不存在就先建）。文件第一行起必须是这段 front matter，`semantic status` 靠它判断这张表审过没有、改过没有：

```yaml
---
reviewed_doc_digest: <scope-lineage semantic digest <run>/docs/<db.table>.json 打印的十六位摘要>
reviewed_packet_digest: <你读的 packet.md 里「packet_digest」那一行的十六位摘要>
high: <高的条数>
medium: <中的条数>
low: <低的条数>
---
```

`reviewed_doc_digest` 取你审读的那一版文档（开始审读前算，审读期间不改文档）；`reviewed_packet_digest` 从你读的材料包照抄，不要从文档里抄；三个计数是整数，没有就写 0，与正文条数一致。缺 `reviewed_doc_digest` 或任何一个计数，这份审读就不会被后续步骤处理；缺 `reviewed_packet_digest` 或抄错，修订就无法记录完成，文档改过之后这张表只能重新审读。不要写 `fixed_doc_digest`：它由修订的最后一步 `semantic fixed` 写入。

front matter 之后，按严重程度列出发现：高 = 读者照页面用会取错行或算错数；中 = 误导或不完整但数字通常对，或把影响用法的推断写成了事实；低 = 措辞、精度。同一个错误出现在几个字段里只算一条，列出全部位置。每条：文档位置（字段路径）、文档原话、材料包事实（原文引用）、应改成什么。最后一行写「高 N、中 N、低 N」。

编号：本轮发现按严重程度编 H1、H2…、M1…、L1…。正文里列旧审读或上一轮发现处理结果的表格，第一列依次编 o1、o2…；第二列抄它在旧文件里的原编号，并带上所在小节（例如「上一轮发现的处理结果 L5」）。一份审读文件里每个编号只指一件事。引用旧发现一律写「旧审读 oN」，或写旧审读里本轮发现的 HN / MN / LN。旧审读不是按这条规则写的，就写「旧审读 <小节>-<原编号>」。

高、中都为 0 时，这张表的状态直接是 `fixed`，低级发现不会被派去修订。这是约定（低级问题不修），不是 `status` 的缺陷。按上面的定义定级：不要为了让某条被修订而调高，也不要因为它反正不修而调低。
