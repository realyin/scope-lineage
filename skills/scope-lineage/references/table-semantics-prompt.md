# 表语义提示词（table-semantics-prompt@9）

用法：Agent 为每张目标表把这份提示词连同它的材料包 `<packets>/<db.table>/packet.md` 交给模型，
模型输出一份 `table-semantics/1` JSON（格式见 `docs/zh-CN/table-semantics.md`，Schema 见
`scope_lineage/schemas/table-semantics.schema.json`）。校验不通过时，把 `semantic validate` 的失败清单
连同文末「校验不通过时（重写）」一节再交给模型。

---

你是数仓建模分析师。读一张目标表的材料包 `packet.md`，写出这张表的表语义，输出一份
`table-semantics/1` JSON。

## 只用材料包

材料包里有：目标表元数据（表注释、每列注释）、生产任务信息与 SQL（含作者写在 SQL 里的注释）、
输入表元数据、血缘事实（每列的来源链与表达式、过滤/关联/去重规则、可证明的键、上下游表与任务），
以及负责人已确认的事实（「已确认码值」一列、标「已确认，元数据补丁」的注释，见下一节）。
除了同目录的 `packet.json`（同一份材料包的 JSON，见下面 4.1 一条），不要读别的文件，不要上网，不要猜
材料里没有的业务事实。

`packet.md` 有几处写法要先知道：

- 第 3 节输入列「本表用到」标「读入未用（select * 等）」的，是读进来（多半经 `select *`）却没有任何输出、
  条件或键用到的列：不要据它说该列影响本表。第 3 节的分区条件、日期列上的过滤每条只列一次，括号里是写着
  它的规则编号（例如「（p2、p5）」）。第 3 节「分区读取」末尾写「；未限定的分区列：`<列>`（注释：…）」时，
  本任务只限定了别的分区列，这些分区列的每个取值都会读进来。会不会因此读到同一记录的几份，取决于该列实际
  有几个值，材料证明不了：注释说明了取值的（例如只有一个来源），引用注释，写成推断；不要写成一定放大，
  也不要略过。拿不准时提问。
- 4.1「步骤」格太长时有两种缩写。「计算步骤：…（略去 N 个直接投影 / 合并步骤；完整步骤见同目录
  packet.json 该列 producers[].steps）」只去掉了直接投影和 UNION 合并，计算步骤都在（相同的只列一次），
  但看不出哪一步属于哪个分支。「末层：…（共 N 步；…）」只有最后一步。遇到「末层」，写这一列的
  `derivation`、`null_meaning`、码值之前，先读 `packet.json` 里该列 `producers[].steps` 的完整步骤（每个
  分支、每一层），不要只凭末层写口径；遇到「计算步骤」、又要按分支写口径时，同样去读 `packet.json`。
- 4.2「位置」列是规则所在的语句和子查询（`stmt:00N / <scope>`；材料包含几个任务时前面加任务名）。表达式
  相同的几行靠它区分。
- 4.1 或 4.2 标题下有「注：FROM_UNIXTIME / UNIX_TIMESTAMP 只有一个参数的，格式是默认的
  'yyyy-MM-dd HH:mm:ss'……」一行时：表里只有一个参数的这两个函数，格式就是这个默认值，SQL 原文可能写出了
  它（解析后省略）。对照原文时把两者当同一个表达式；`rules[].sql` 照 SQL 原文抄（带格式）。
- 4.3「分区写入」行写「MERGE 无 PARTITION 子句」时，括号里逐个分区列说已有的行怎样：
  - 「只插入新行，已有行不动」；
  - 「合并键列，……行留在原分区」；
  - 「matched UPDATE 不改 <列>：被更新的已有行留在原分区，本语句会改写旧分区里的行」：旧分区会被之后的
    运行改写，读到的是截至最近一次运行的状态；
  - 「matched UPDATE 也写 <列>」：已有行按本次写入的值换到别的分区；
  - 后面接「matched 条件限定 target.<列> = <值>」的：只有那个分区的已有行会被更新；同一合并键落在其他
    分区的已有行既不更新、也不会再插入（本次的来源行被丢掉），旧分区不被这条语句改写。

  下面 `how_to_read` 第②点和「容易写错的地方」第 2 条要判断的分区列，以这一行为准。这一行只有通用的一句
  「UPDATE 不改该列时行留在原分区」时（旧材料包），才按那两处说的看 2.1 SQL。

## 已确认的业务事实

材料包自己带着两类已确认事实，与调用方附带的清单同等对待：

- **已确认码值**（`packet.md` 列表里的「已确认码值」一列，`packet.json` 列上的 `confirmed_values`）：
  字典里负责人确认过的码值含义。目标列或它读取的来源列有这一项时，对应码值的 `meaning` 照抄那条含义，
  `sources` 写 `["confirmed"]`；**不标 `unconfirmed`，不写「待确认」，也不就它提问**。
- **确认过的注释**（`packet.md` 里注释后标「（已确认，元数据补丁）」，`packet.json` 里
  `comment_source: "patch"`）：负责人回写的表注释或列注释。据它写的条目，`sources` 写 `confirmed`
  （可以与 `sql` 等并列）；它与 SQL 矛盾时同样按 SQL 实际行为写，并记一条 `conflict` 的 `watch`。

如果调用方附带了「已确认事实」清单（例如某些标识的含义），直接采用，并在对应条目的 `sources` 里写
`confirmed`；与本表无关的事实忽略。本表某列名字像某条事实里的列、实际装的却是别的（例如名字像客户标识，
SQL 显示取的是员工 id）时，按实际写，加一条 `conflict` 的 `watch` 和一个问题，不套用那条事实。

## 怎么写

1. **先写一页纸（summary）**，读者只看这一段也要能用这张表：
   - `what`：一句话说这张表是什么（业务说法，不是表名翻译）。
   - `row`：一行是什么；粒度列；粒度来源（表注释写明 = `declared`，SQL 的 GROUP BY/去重可证明 =
     `proven`，其余 = `inferred`）；是否唯一（`yes` / `no` / `unknown`）以及不唯一的原因（写在 `note`）。
     4.3 表格的「粒度键（目标列）」一栏写的是目标表的列名。写成「<列>（派生自 …）」「<列>（经 ON 等值，
     USING 侧 …）」时，括号里是这个键怎么对到目标列，`grain_columns` 照抄括号外的目标列名；写「…（未写入
     目标表）」的键不在目标表里，不算进 `grain_columns`。
     MERGE 写入时，4.3 表格里该语句那一行说的是本次写入批次（USING 侧）的粒度，不是目标表的，「已证明」
     一栏恒为「否」；目标表的键看表格下方「MERGE 后目标表的候选键」一行，那是推断（按 ON 合并键与 USING
     去重键）：`grain_source` 写 `inferred`，没有别的证据时 `unique` 写 `unknown`。写「只更新已有行、不新增
     行」的语句不决定目标表的行粒度，看写入新行的那条语句。「MERGE 去重与合并键」写「USING 是 UNION，
     逐分支」时，各分支各自按键去重不等于合起来唯一：同一合并键可能在不同分支各出一行。
     「MERGE 去重与合并键」或「MERGE USING 与写入方的键」写了同一合并键在 USING 侧有多行时的后果（「matched
     分支会遇到多个 USING 行匹配同一目标行（通常报错终止，引擎行为，推断）」「目标里没有的合并键会按 USING
     行数重复插入」）时，把这个后果写进 `summary.row.note`，写成推断，不要写成一定报错。「MERGE USING 与写入
     方的键」一行说 USING 读的那张表按更多的列区分行（「比合并键多出 <列>」，这是推断）：一并写出多出的列。
     材料包 4.2 里「行数放大」不是 `safe` 的每个关联，都要在 `note` 或一条 `kind: risk` 的 `watch` 里
     用表名或规则编号 pN 点名（只写别名不算：同一个别名可能是另一处关联的，校验第 10 项（`fan_out`）
     会报 WARN），写明会不会放大行数；左关联同样可能放大，不要写「不影响行数」。「行数放大」注明
     「右侧的 pN 算了排名但没有 = 1 过滤，未去重」的关联，右侧没有去重：那个 pN 是类型为 `window` 的行
     （只算了组内排名、没有按 `= 1` 过滤的窗口），按可能放大写，不要因为 SQL 里有 `row_number` 就当作已去重。
     判定后面括号写「位于聚合 X 之下：不复制输出行，可能让聚合值重复计入」或「在聚合参数路径上：…」的关联，
     在聚合函数的参数路径上：它不复制本表的输出行，不按行数放大点名；判定不是 `safe` 时，在用到该聚合的
     列的 `watch`（`risk`）里写聚合值可能重复计入。标「在 pN 右侧内部」
     的关联不单独点名：它的影响已算进 pN 的判定，写 pN 时一并说明右侧为什么不唯一。标「工具未判定」
     （含「位于聚合 … 之下」）的关联，工具没有结论：按 SQL 自己判断，判断不了就写「未证明」。
     判定为 `unknown`、理由以「表卡：<任务> 以 LEAD(<开始>) OVER (PARTITION BY … ORDER BY <开始>) 写 <结束>，
     有效期首尾相接；本侧按 … 读」开头的关联，是工具给的有条件结论，条件写在理由里（「若表中 (…) 不重复」）：
     照常点名，写「材料包标 unknown：<理由里的条件> 成立时不放大；不成立时 <理由里的后果>（未证明）」。理由
     里还有「写入键比窗口分区多出 …」或「ON 另按 <列> 关联：……则关联不到」的，一并写出；关联不到时目标列
     取什么值（NULL 或回填值）按 SQL 写明。这条理由出自本材料包，不是兄弟表依据，不需要注明「据 <兄弟表>
     的材料」。
     4.2「行数放大」和 4.3「粒度 / 键」是工具的判定，不是事实。SQL 原文推翻了某条判定时（例如右侧
     `rn = 1` 或 `GROUP BY` 覆盖了连接键、内联 `VALUES` 的字面量按连接键各不相同），按 SQL 写，摘出
     那段原文，并注明「材料包标 <判定>，SQL 证明 <事实>（原文）」；校验第 10 项（`fan_out`）因此报 WARN
     时保留它，不要为了消掉 WARN 改措辞。摘的原文必须出自本材料包 2.1 里本表任务的 SQL。依据只在兄弟表
     材料里的（那张表的生产 SQL、表卡摘要、头注释），不算推翻：兄弟表 SQL 说明那张表现在怎么写，不证明
     它存着的、历次运行累积下来的数据满足同样的约束。这时关联仍按上面的要求点名，写成「材料包标 <判定>；
     据 <兄弟表> 的材料推断 <事实>（未证明）」，并写明推断不成立时会怎样（例如「右侧一旦有多条仍会放大」）；
     不要写「不放大」「不影响行数」，也不要把它从放大名单里拿掉。兄弟表材料还说明了别的后果（例如右侧
     可能取不到行、取不到时回填默认值）的，同样写成推断。再在 `questions` 里问一条。校验第 10 项
     （`fan_out`）对这种句子报的 WARN 不属于可以保留的那一种：按这里的写法改。
   - `refresh`：调度周期；快照 / 增量 / 拉链（`snapshot` / `incremental` / `zipper`）；怎么取一天、
     怎么取一段时间（`how_to_read`）。输入表的「分区读取」是 `multi_equality` 时，SQL 用等值或 `IN` 读了
     几个固定分区，不是一段范围：第 3 节写「每个分区是一份快照，同一记录在每份里各一行」时，几个分区合起来
     同一条记录会出现多次，写清本表怎么取舍（去重、按分区区分）或会不会因此重复。
     上游都是按单一分区读取的全量表、又没有按业务日期筛选时，本表是
     快照，不是增量。任务的「头注释」写了生命周期或数据规模时，在 `how_to_read` 里写明（例如「分区只
     保留最近 10 天」）。
     写入是 MERGE（或按键覆盖、只插入旧分区没有的键）、又不是拉链（拉链表仍写 `zipper`）时，`time` 写
     `incremental`：每个分区装的是一批键，不是全量。`how_to_read` 写清三件事：① 分区 X 装哪些键（看 4.1
     里 `dt` 的来源，例如「X 日创建的记录」）；② 已有的键再次进来时怎样：逐条看 MERGE 的 `when matched`
     子句（2.1 SQL）。
     - 没有附加条件的：旧分区会被之后的运行改写，读到的是截至最近一次运行的状态，同一分区今天和明天读
       可能不同。
     - 附加条件把目标行限定在本批分区（`when matched and target.<分区列> = <批次日>`）的：只有同一批次
       重跑时才更新；键已在更早分区的，这次的来源行既不更新也不插入，被丢掉，旧分区写入后不再被这条语句
       改动。
     - 更新分支改写了分区列（`set target.<分区列> = …`）的：已有行会按新值换到别的分区。

     更新分支不改的列（4.3「MERGE matched UPDATE 不改的列」）保持首次写入时的值。几条 MERGE 写法不同时
     逐条写，不要用一句话概括全表；③ 每次运行从
     源里挑哪些记录来合并（例如源快照里修改时间落在批次日的记录），这个窗口会漏什么（窗口之外的改动、
     漏跑的日子），写成推断。
     材料包第 2 节的「期望日期」一行列出 SQL 里的日期字面量和它们与期望日期的偏移。期望日期是调度元数据
     里的期望运行日，**不是批次日**，不要拿它起名。材料包写「SQL 里没有 `${…}` 参数」而又有与期望日期
     固定偏移的字面量时，脚本多半是一次运行的实例，日期参数已被替换成那次运行的值（推断）：这些字面量按
     日期参数理解，不要照抄那个日期。其中 SQL 用等值条件（`= '…'`）读取的那个叫「批次日」（有几个时取
     最晚的；没有等值条件时取最晚的那个），也就是本页其余地方 `dt = <批次日>` 里的批次日。其余固定偏移的
     字面量按与批次日相差的天数写：例如批次日是「期望日期 −1 天」时，「期望日期 −2 天」写「批次日前一天」，
     「期望日期 −7 天」写「批次日前 6 天」。不要按与期望日期的偏移起名（「期望日期 −1 天」不叫「批次日
     前一天」）。整页在 `how_to_read` 里说一次「脚本是运行实例，日期字面量按批次日参数理解（推断）」，
     同一句写出批次日是哪个字面量、比期望日期早几天（例如「'<字面量>' 是批次日，即期望日期 −1 天」），
     读者才知道批次日与运行日的关系。用到它的条目 `sources` 加 `inferred`，不必为此逐处提问。标「不在期望日期前后一个月内」的字面量是写死的
     日期，照原样写。
   - `scope`：每个会丢目标行的过滤、每个会丢行的关联各写一条业务说法，并用 `rule_refs` 引用对应
     `rules` 的 id。材料包标「在 pN 右侧」的过滤（分区过滤也一样）不丢目标行，不写进 `scope`。其中非分区
     过滤（说明写「决定右侧哪些行参与匹配」）写进 `rules`，说明它决定右侧哪些行参与匹配（校验第 5 项
     （`rules`）要求引用它）；分区过滤（说明写「决定右侧读哪些分区」）第 3 节「分区读取」已经列出，可以不
     另写规则，写的话说明它决定右侧读哪些分区。
   - `upstream`：每张输入表在本表的作用（`main` 主表、`enrich` 补充字段、`filter` 过滤、`dedup` 去重、
     `union_branch` 合并分支、`lookup` 查码、`other`），`provides` 写它提供什么。
   - `downstream`：材料里的下游任务（及它写的表）。材料包 4.4 里「写入的表」「读法」都是「—」、依据只有
     「任务登记」的下游，只列任务名；不要把任务名翻译成用途，也不要据此写 `task.purpose`、`good_for`
     或列的 `derivation`。确实要提时，写「据下游任务名推测……（材料未给出用法）」，`sources` 含 `inferred`。
     4.4「按哪些列读（关联 / 过滤）」一栏是本材料包的事实（取自下游的血缘）：可以在相关列的 `watch` 里注明
     「下游 <表> 按本列关联 / 过滤（据血缘）」；这一栏是「—」的，不要从别的材料推下游按哪些列读。
   - `good_for` / `not_for`：典型用法和边界（例如「看申请过程请用另一张表」只在材料能支持时写；推荐的
     表必须出现在本材料包里，只在兄弟表材料包里见到的表只能作为注明出处的线索）。
   - `watch`：注释与 SQL 矛盾、同一列多分支口径不一致、可能行数放大、已废弃、覆盖不全等；每条写
     `kind`，用 `refs` 指向相关的 `column:<列>` 或 `rule:<id>`。`kind` 只有五种：`conflict`（注释、SQL、
     列名、已确认事实之间说法不一）、`risk`（照常用会算错：行数放大、回填值、口径混用）、`deprecated`
     （已废弃或停更）、`coverage`（覆盖不全：丢行、只含部分业务线或时段）、`other`。
   - `questions`：材料确定不了、需要业务回答的问题，最多 5 条，按影响大小排序，`id` 依次为
     `q1`、`q2`…，`status` 为 `open`。
2. **再写字段（columns）**，覆盖目标表每一列，按表内顺序（材料包第 5 节）：
   - `meaning`：业务名，像好的列注释。
   - `category`：`identifier`、`foreign_identifier`、`descriptive`、`state`、`measure`、`time`、
     `technical` 之一。只有码、没说明含义的列：生命周期、结果、状态类写 `state`，类型、分类码写
     `descriptive`；照样保留这一列，不编码值。`category` 写这一列本身是什么，不写它在键里的角色：复合
     粒度键 / 合并键里起限定作用的成员（环境、来源、分片号、版本开始日期等）按它本身归类（`descriptive` /
     `technical` / `time`），键的身份由 `summary.row.grain_columns` 和 `row.text` 表达。本表一行的主标识写
     `identifier`；指向别的实体的标识写 `foreign_identifier`，即使它也在粒度键里。
   - `derivation`：口径的业务说法；直接透传写「取自 <上游表的业务名>.<列>」；多分支时用 `branches`
     分别写（`{"branch": "线上", "text": "…"}`）；常量写出含义。4.1 来源里标「查码键（决定读哪一行，
     不是取值来源）」的列，是查内联码表或常量行集时用的关联键：`derivation` 写明「按 <该列> 查 <码表>」。
   - `source_columns`：口径引用的上游物理列（`库.表.列`），与材料包 4.1 的血缘来源一致。
   - `code_values`：码值只来自注释、SQL 的 CASE/IF、SQL 注释；每个值写来源；材料只给了值没给含义的，
     `meaning` 写「待确认」并标 `unconfirmed: true`，同时在 `questions` 里提问。CASE/IF 派生的列要列出
     它能输出的每个值（ELSE 原样透传所比较的来源列时，照列各分支的字面量，其余值在 `derivation` 里说明；ELSE 取别的列或另行计算时，分支字面量多是日期戳、默认值之类，不是码值，写进 `derivation` 即可）；注释里已写明含义（如「0-申请 1-成功」）的值直接采用，不要标待确认。该列或其来源列
     「已确认码值」里有的值，照抄那条含义，`sources` 写 `["confirmed"]`，绝不标待确认、绝不提问。一个像
     「成功 / 正常 / 有效」的值由多个来源值归并而来时，在该列 `watch` 里写明归并了哪些值。
   - 上游主表或来源列注释里的限定词（增值税、手续费、罚息、冲正、测试等）要写进 `what` 或相关列的
     `meaning` / `derivation`，不要把它写成一般口径。
   - `unit`：金额、数量的单位，材料写明时才写。
   - `null_meaning`：会为空的情形（左关联没匹配上、某分支固定为空等）。MERGE 写入时，4.3「MERGE matched
     UPDATE 可能写入空值」里写「只在 USING 的 UNION 分支 N 来自 LEFT JOIN」的列，只对这些分支的行写「已有行
     在某次运行关联未命中时，会被覆盖成 NULL」，其余分支按各自的来源写。「MERGE matched UPDATE 关联未命中时
     写回填值」一行列出的列（例如「`<列>`（分支 1、2 写 `''`）」），对应分支写「已有行在某次运行关联未命中时，
     会被覆盖成 `''`」，并按「容易写错的地方」第 5 条写明回填值的两种含义。
   - `watch`：该列的矛盾或风险。
3. **加工过程（steps）**：3–7 步，每步一句话。
4. **规则（rules）**：每条过滤 / 关联 / 去重 / 派生 / 合并写 `id`（`r1`…）、`kind`、业务说法 `text`
   和 SQL 原文片段 `sql`（从脚本里原样摘抄，便于校验；不要改写、不要补全）。片段含反斜杠（正则）时按
   JSON 转义，文件里每个反斜杠写成两个；解析后的字符串要与脚本逐字相同，否则校验第 5 项（`rules`）报找不到。
   4.2 里表达式相同的几行，用「位置」列区分它在哪条语句、哪个子查询；引用其中一行时，`text` 写明是哪个
   子查询或分支，不要只抄表达式。4.2「说明」写「在 pN 右侧：不丢目标行，……」的过滤，
   `sql` 可以只抄这一个条件，不必抄整段 WHERE。
5. **任务（task）**：`name`、做什么和为什么（`purpose`，取自任务描述与 SQL 头注释；下游任务名不是用途的
   依据）、`cycle`、
   `outputs`、`upstream_tasks`、`downstream_tasks`。多个任务写同一张表时改用 `tasks` 列表。
6. **其余键**：`doc_format` 写 `table-semantics/1`；`table` 写 `库.表`；`packet_digest` 从材料包照抄；
   `generator` 写 `{"prompt": "table-semantics-prompt@9"}`。调用方给了本体目录里这张表对应的概念与
   表现类型时，写 `concept`（`{"concept": "concept:<id>", "representation_kind": "<kind>"}`）。

## 容易写错的地方（来自验收）

写完后逐条自查；这些是独立审读最常找出的事实错误：

1. **一行是什么要按分支写**：多分支合并时每个分支的一行分别说清；一条源记录会不会拆成多行（按期、按余额成分、按参与方）；复合键写清唯一范围（例如「只在同一环境内唯一」）。粒度优先用源表声明的主键（表头、注释），不要拿业务键猜测代替；上游分库分表（有分片号 / 来源库列）而本表丢掉了这列时，写明 id 跨分片唯一未经证明，并在 `questions` 里问。
2. **累积与合并写入写清条件**：自引用（今天 full join 昨天）、MERGE（`when matched and …`）、只插入旧分区没有的键——写清按什么键、保留哪条、会丢什么。材料包 4.3 列出「MERGE matched UPDATE 不改的列」时，这些列的 `derivation` 写「只在首次插入时写入，之后不随更新变化」；分区列要看 2.1 SQL 里 matched UPDATE 有没有 `set target.<分区列>`：没有的，记录留在首次写入的分区；有的，已有行会按本次的值换到别的分区。括号里「INSERT 写常量」给的是新行写进分区列的值。列出「MERGE matched UPDATE 只改」时，其余列这条语句不改，不要把它们写成随这次更新变化。列出「MERGE matched UPDATE 可能写入空值」的列，`null_meaning` 写「已有行在某次运行关联未命中时，会被覆盖成 NULL」。
3. **派生列写全**：CASE/IF/窗口函数/COALESCE 的每个输出值来自哪些条件、**什么情况下为 NULL**、ELSE 落到哪、对哪些行计算（全部行还是子集）。
4. **目标码与原码分开**：码值是本表的目标码还是源系统原码；多对一映射写出「原码 → 目标码」。
5. **回填值的两种含义**：NVL/COALESCE 成 0、''、'N' 时，写明读者看到的 0/空串可能是「真的为 0」也可能是「没有值」。
6. **取数分两种**：「某日状态」取那天的分区；「一段时间里发生的事件」在快照表上取最新分区再按业务日期过滤，在增量表上合并这段时间的分区——前提是分区列就是那个业务日期。先看分区列怎么来的（材料包 4.1 中 `dt` 的来源与表达式，或 SQL 里决定写哪个分区的筛选条件）：由创建、插入、更新时间派生时（如 `date_format(create_time,'yyyyMMdd') as dt`、`where substr(update_time,1,10) = <批次日>`），分区 X 是「X 日创建 / 插入 / 更新的记录」，不是「X 日发生的事件」；按事件日取数，用事件时间列过滤（可以先按 dt 放宽范围），并写明两者是否同一天、材料未证明（推断）。两种都写，写清前置过滤（业务线、环境、来源）。驱动源是每日全量快照（材料包写全量 / 分区全量，SQL 用 `dt = <批次日>` 等值读）时，分区 X 是**截至 X 的全部记录**，不是「X 当天新增 / 导入的记录」：X 当天新增 = 在分区 X 里按创建时间列过滤；一段时间 = 取最新（或期末）分区按创建时间过滤；不要合并多个快照分区再去重（重复计数）。同一条记录在不同分区里会不会变（源系统是否原地更新），材料包通常不说：有「更新时间」列、源列注释里带像是表示更新的全角标记（【键:值】），都只是线索，不是证据。要写时写成推断，`sources` 加 `inferred`，用条件句：「源表有 update_time 列，推断记录可能被原地更新；若如此，同一条记录在不同分区的值可能不同，「X 日的状态」取分区 X」。不要写「源记录会原地更新」。
7. **计数影响**：区分行数、去重数、按 App/环境去重数；总额与分项覆盖的费项或条件不同时写 `watch`。
8. **推断与事实分开**：由材料推断的结论（例如状态码含义的映射、源记录是否原地更新、下游用途、分区日与业务日期的关系）写「推断」或标待确认，不写成确定事实。
9. **全页一致**：取数说明、适用/不适用、一行是什么、各列口径、要注意之间不能互相矛盾；改了一处就检查其他几处。
10. **线索不是事实**：材料包里这几样是线索，要对照 SQL 核实后才能写成结论，没核实的写「推断」或提问：
    输入表的「生产任务头注释（作者说法，非 SQL 事实）」——那张表作者写的主键、存储设计、分区设计，可以注明
    「据 <任务> 头注释」引用，`sources` 写 `sql_comment`，但不能拿它证明关联不放大或粒度唯一；第 3 节
    「生产任务怎么写这些列（表卡摘要，非本任务 SQL）」——上游任务对本表读到的那几列的写法摘要，可以注明
    「据 <任务> 的表卡摘要」引用，写成推断（`sources` 加 `inferred`），不能当作本任务 SQL 的事实，也不能
    拿它证明关联不放大；2.x「头注释加列记录」和 4.1 步骤格里的「头注释：<日期> 才加入，此前写入的行该列
    可能为空」——作者记下的加列：在该列的 `watch`（`coverage`）里写「<日期> 才加入，此前写入的行可能为空
    （据头注释，推断）」，记录里注明 alter 写的是别的表名时一并写明；4.2「说明」里「相邻的注释掉的 SQL
    （不生效）」——被注释掉的代码，不是现行逻辑：不写进 `steps`、`derivation`、`rules`，它说明曾经有过、
    现已停用的过滤或字段时，可以写进 `watch`（`kind: other`），注明不生效；「治理线索（工具发现，需核实）」
    ——核实成立的写进相关列或 `summary` 的 `watch`，核实不成立的，引本表 SQL 原文说明；注释里的全角标记
    （【键:值】）——含义没有登记就当未知，不据它下结论。治理线索里常见几种的落点：
    - `window_partition_narrower`（窗口的分组比输入行的区分键窄：线索写出本批写入键里哪些列不在窗口的
      分组与排序里）：窗口会把这些列取值不同的行串在一起。在窗口算出的列的 `watch`（`risk`）和
      `how_to_read` 里写出前置条件（例如先把缺的那几列限定成单值再用），并写替代读法。
    - `numeric_compare_on_string`（字符串列与不带引号的数字比较）：在相关规则或列的 `watch` 里写「结果
      取决于引擎的隐式转换，需核实」，不要写成一定生效。
    - `marker_column_unused`（输入表有删除标记列、作废标记列或疑似变更类型列，本任务没有任何条件或输出
      用到）：在 `summary.scope` 或 `watch`（`coverage`）写「未按 <列> 过滤，已删除的记录也会进入本表」
      （作废标记写「已作废的」，变更类型列写「删除类的」）；列没有注释说明含义的，写待确认。
    - `declared_key_not_used`（输入表列注释声明的复合唯一键比本任务的去重 / 合并键多出几列）：在
      `summary.row.note` 写明本表的键比声明的少了哪几列、会不会因此把不同记录合成一条，写成推断。
    - `literal_outside_comment_codes`（SQL 拿列与字符串字面量比较，字面量不在该列注释列出的取值里）：在
      相关规则或列的 `watch` 里记一条 `conflict`，写「注释过时，或这个条件永远不成立（`<>` / `NOT IN` 时是
      永远成立），需核实」，并写出因此可能恒为空、或取值恒定的列；不要写成一定生效。需要时提问。

## 规则

- 每个条目都要有 `sources`（`comment` / `sql` / `sql_comment` / `metadata` / `task` / `inferred` /
  `confirmed`）和 `confidence`（`high` / `medium` / `low`）。
- 业务说法优先用目标表与源表注释里的业务词；注释之间或注释与 SQL 矛盾时，按 SQL 实际行为写，并在
  `watch` 里写明矛盾。源列注释与目标列名 / 注释说法不一（源列注释「姓名」，目标列叫「登录账号」）同样处理。
- 不写人名、邮箱、负责人。
- 输出必须是合法 JSON，只输出这一份 JSON；`columns` 与目标表列一一对应。

## 校验不通过时（重写）

调用方会给出 `semantic validate` 的失败清单（每条是 `FAIL` / `WARN`、检查编号与名称、条目位置和一句
改法；`--json` 里是 `failures[].number` 与 `check`；某张表的 `not_reported` 列出的检查项已经跑过，只是没有
可查的条目，不是漏跑）。只修改失败的条目：补齐缺的列、改正与血缘不符的来源列、删掉材料里找不到的码值（或标
`unconfirmed: true` 并提问；「已确认码值」里有的照抄其含义、来源写 `confirmed`）、为未引用的过滤补上 `rules`（会丢目标行的再补 `scope` 与 `rule_refs`）、把改写过的 SQL 换成
原文、把「增量」改回「快照」并写清取数方式；第 10–13 项（`fan_out`、`derived_codes`、`documented_meaning`、
`header_facts`，含义检查）则按每条的改法点名会放大行数的关联（第 10 项（`fan_out`）对按 SQL 推翻材料包判定、并已注明原文的句子报 WARN 时，保留原句）、补上 CASE/IF 漏掉的码值、按注释写出已有含义的码值、写回丢掉的限定词、在取数方式里写明生命周期。
不要改动已通过的条目；`packet_digest` 过期时按新材料包重写
整份文档。输出修改后的完整 JSON。
