# The `semantic.json` / `semantic.md` task-semantic description (semantic-json/1, semantic-md/1)

`scope-lineage describe` derives a **deterministic semantic skeleton** of a write statement from
its `lineage.json` (plus the `diagnostics.json` beside it): `semantic.json` (the primary artifact)
and its rendering `semantic.md`. It answers a different question from
[mapping.md](mapping-doc.md) — mapping.md answers "where did this column come from", while the
semantic pair answers "what does this task do, what does one row of the output table represent,
and what does each field mean".

> The rendered `semantic.md` is written in Chinese — its section titles, source tags, and line
> labels are fixed Chinese strings and are part of the format. This page quotes them verbatim
> wherever the grammar depends on them.

## Positioning: a derived view, not a business definition

- `semantic.json` / `semantic.md` are a **derived view** of the versioned contract (a sibling of
  mapping.md): every statement in them comes from `lineage.json` / `diagnostics.json` and links
  back by `scope_id`, `logic_block_id`, or `mapping_chain_id`. The documents carry no "orphan
  facts" from outside the contract.
- **The facts themselves always live in `lineage.json`.** `semantic.json` is the compressed view an
  Agent or a RAG pipeline fetches by path; `semantic.md` is the rendering a person reads end to
  end. Both are produced from one dict, so they cannot drift apart.
- Every line carries a source tag. There are four:

| Tag | Meaning | Where it appears |
| --- | --- | --- |
| `SQL事实` ("SQL fact") | Written in the SQL itself: filters, join keys, group-by keys, window specs, expressions, source fields | Action lines in section 3, the rule table in section 4, step lines in section 5 |
| `元数据事实` ("metadata fact") | Table/column comments, column types, partition columns — from `related_metadata` | The target-table line in section 1, target comments and types in section 5, metadata coverage in section 6 |
| `SQL事实+元数据事实` | One line carrying both a SQL source and that source's comment | The "sources" line in section 5 |
| `结构推断` ("structural inference") | What the SQL structure **proves**: output shape, grain, candidate keys, fan-out risk, window intent, structural role | All of section 2, window intents in section 3, structural roles in section 5 |

- **`结构推断` is not a business definition.** "Partitions by `customer_id`, orders by `event_time`
  descending, keeps row 1" is a provable structural fact; "takes the customer's latest status" is a
  business inference and is not in this artifact. Core deliberately publishes no business entity
  names, no business table types (wide table / allow-list / metric table), no module names, no "the
  goal of this task is…", and never guesses a role from a column-name suffix — those absences are
  the design, not a gap. The business profile is generated by an Agent following
  [`skills/scope-lineage/references/semantic-profile-prompt.md`](../../skills/scope-lineage/references/semantic-profile-prompt.md)
  and labelled separately as `LLM推断` / `待业务确认`.
- Stability tiers:
  1. the contract ids the documents reference (`scope_id`, `logic_block_id`, `mapping_chain_id`,
     table and column names) are as stable as `lineage.json` itself and can be used as join keys
     back into the JSON;
  2. the `semantic.json` key names and the `semantic.md` line grammar are only guaranteed stable
     within one `doc_format` major version (currently `semantic-json/1` and `semantic-md/1`); a
     structural change increments that version number;
  3. the Chinese wording and the layout may be adjusted without incrementing the version number, so
     machines must not depend on any text shape not listed in the "Line grammar" section below — a
     machine consumer should read `semantic.json`.

## Usage

```bash
# One statement: semantic.json and semantic.md are written next to lineage.json
scope-lineage describe --lineage /path/to/task/lineage.json

# A corpus directory: lineage.json is found recursively; --out mirrors the input tree
scope-lineage describe --lineage /path/to/corpus --out /path/to/docs

# JSON only; or render a subset of sections (a 112-field task keeps only section 5's table)
scope-lineage describe --lineage lineage.json --format json
scope-lineage describe --lineage lineage.json \
  --sections overview,shape,fields_table,confidence

# With the three corpus layers: table cards, the glossary, the concept layer
# (--ontology accepts ontology-json/2 only)
scope-lineage describe --lineage /path/to/corpus --out /path/to/docs \
  --tables tables.json --glossary glossary.json --ontology ontology.json
```

Python API (consumes contract document dicts, the same code path as writing the files):

```python
from scope_lineage import build_semantic_profile, render_semantic_markdown

profile = build_semantic_profile(lineage_document, diagnostics_document)
markdown = render_semantic_markdown(profile)                       # all seven sections
short = render_semantic_markdown(profile, sections=["overview", "fields_table"])
```

- The input handling is identical to `render`: `--lineage` takes one `lineage.json` or a directory
  searched recursively for them, the sibling `diagnostics.json` is paired automatically, and
  `--out` mirrors the input tree.
- Both contract shapes are accepted: a **statement document** (`schema_version: "1.0"`) and a
  **task document** (`schema_version: "2.0"` with `artifact_kind: "task_lineage"`). Any other
  version is skipped and counted in directory mode (`skipped_unknown_version=N` in the run summary)
  and raises an error in single-file mode (exit code 1).
- A document that cannot be read costs only itself: when a `lineage.json` or its sibling
  `diagnostics.json` is not valid JSON, or its top level is not an object, directory mode writes
  one line per file to stderr, counts it as `skipped_unreadable=N`, and describes the rest of the
  tree; single-file mode prints one line and exits 2.
- `--format` takes `json`, `md`, or both (default `json,md`); any other value is an argument error.
  `--sections` affects `semantic.md` only — `semantic.json` is always complete — and an unknown
  section name is reported by name and exits 1.
- When there is no `diagnostics.json` in the same directory, describing proceeds as usual, but
  section 6 states "无 diagnostics 文档" ("no diagnostics document") explicitly and the run summary
  counts it in `missing_diagnostics=N`, rather than staying silent.

## Incremental runs: `--incremental` / `--no-cache` / `--cache-from`

One or two tasks changed, and the rerun still reads and re-derives every task in the
corpus. `--incremental` narrows that pass to the tasks whose fingerprints moved:

```bash
scope-lineage describe --lineage /path/to/corpus --out /path/to/out --incremental
```

- It writes two disposable things under `--out`: `.scope-lineage-corpus-index.json` (the
  sha256 of each task's `lineage.json` / `diagnostics.json`, plus one sha256 over the
  options that steer the derivation) and `.cache/` (the documents each task was described
  into -- `describe` has no corpus-level merge, so the documents are its facts).
- `describe` has no corpus-level merge -- one task is one document -- so a task whose
  fingerprints, options and already-written `semantic.json` / `semantic.md` all stand
  still is skipped whole, and a deleted or edited output is described again.
- **Another corpus's cache can be reused too** (Q7): `--cache-from <dir>` names a further
  fact cache -- the `--out` of another run, or the `.cache/` inside it. A task another
  corpus has already described (identical `lineage.json` / `diagnostics.json` bytes,
  identical options digest) has its `semantic.json` / `semantic.md` copied in rather than
  rendered again, and the borrowed file lands in this run's own `.cache/` as well.
  Repeatable, tried in the order given and after this run's own cache; it implies
  `--incremental`, and `--no-cache` still wins. The corpus path is **not** part of the
  options digest: the same task has to describe the same wherever it was parsed.
- Fact files are keyed by task name, and two corpora may hold different tasks under one
  name. What decides a borrow is the fingerprint and the options digest recorded inside the
  file, not the file's name, so a task of the same name and other contents is described again.
- With `--metadata-patch` no task is skipped: `patch_unmatched` answers "this confirmed
  comment matched nothing **in the whole corpus**", which is only true when every task
  was actually described.
- A changed option invalidates the whole index and recomputes everything: the **content**
  of the `--overrides` file, `--format`, the `glossary.json` / `tables.json` / `ontology.json` read back,
  and the tool version. An index or a cache file written by another subcommand (a
  `command` or `doc_format` that disagrees) is ignored the same way.
- The summary line gains `reused=N, recomputed=M, removed=K`: how many tasks were reused,
  re-derived, and have disappeared from the corpus. With `--cache-from` the first counter
  reads `reused=N (borrowed=B)`, `B` being the tasks borrowed from another corpus.
- Without `--incremental` the run is the full one it always was, reading and writing
  neither index nor cache; `--no-cache` deletes both first and then runs in full.

### The task document's outer wrapper

A task document (`schema_version: "2.0"`) does not flatten the seven blocks at the top level. It
wraps them in task-level facts, with one complete statement profile per write statement:

| Key | Content |
| --- | --- |
| `doc_format` | Always `semantic-json/1` |
| `artifact_kind` | Always `task_semantic`, which is what tells it apart from a statement profile |
| `task_id` | The task identifier (from the contract's top-level `task_id`) |
| `lineage_digest` | A content digest of the source task document |
| `produced_tables` | The final produced tables, from `final_table_states`, with session-scoped relations and `directory:` writes excluded |
| `warning_counts` | The whole script's warnings counted by type: the deduplicated **union** of the top-level (script-scoped) list and every statement's own `statement_diagnostics` entry; `null` when no diagnostics document was supplied |
| `statements` | One statement profile per write statement, with exactly the seven-block keys above |

### What each block holds, and its vocabulary

| Block | Key sub-keys | Vocabulary (the implementation is authoritative) |
| --- | --- | --- |
| `task` | `target_table_comment`, `target_table_domain` / `target_table_project` / `target_table_owner` (the target's business placement, copied from the metadata's table-level facts; `null` means the metadata did not say), `partition`, `instance_dates[]`, `driving_tables[]`, `structural_summary`, `target_metadata_source`, `header_comments[]`, `meta` | `partition.mode`: `static` / `dynamic`; `target_metadata_source`: `schema` / `target_ddl` / `null` (neither input described the table); `header_comments[]` is a verbatim copy of the contract's `statement_comments` (the statement's header comments, the author's own words; always present, possibly empty; when a script's opening block is written above a `SET` or another unmodeled statement, the contract has already merged it into the first write statement, so it appears here too); `meta` is a verbatim copy of contract 2.0's top-level `task_meta` (including B4's `upstream_tasks` / `downstream_tasks`, two arrays of task names: that is **scheduling registration**, not the same thing as the corpus-proven `downstream_consumers`), and is `null` for a `.sql` input or when no task metadata was supplied — `null` means nothing supplied it, not that the task has no owner or schedule. Both are **quotations**, not assertions by this view: a comment and a column comment in the metadata may contradict each other, and the artifact does not adjudicate for the author; `instance_dates[]` (WI-2.9) is the set of **date-shaped literals** this statement's equality date filters pin, unquoted, deduped and sorted (`['20260814']`); `[]` means no filter pins a day — it is substituted by a `${…}` variable, or there is no date filter at all — and never that the statement reads every day. The test is the constant's spelling alone (a `yyyyMMdd` / `yyyy-MM-dd` / `yyyy/MM/dd` prefix), read from the same comparisons `hardcoded_date_literal` reads, so the two can never name different days; `driving_tables[]` (B2) names the physical table **every output row comes from**, each entry `{table, via_scopes[], lateral_view_scopes[]}`: the walk starts at ROOT and follows the FROM item only (a JOIN's right side is never the FROM item; a RIGHT JOIN swaps sides, a FULL JOIN takes both, a UNION takes all its branches) and a LATERAL VIEW does **not** stop it -- an explode multiplies the driving table's rows rather than replacing the driving table -- until a physical table ends it. `via_scopes[]` runs in the same direction as `grain.via_scopes` (from ROOT down, ROOT excluded) and `lateral_view_scopes[]` are the scopes on that path that carry a LATERAL VIEW. **Every shape has a driving path** (P3): an aggregated or deduplicated ROOT descends from its aggregating / deduplicating scope's left-most FROM item exactly as a projection does, and a MERGE answers with its USING side. The row *count* is a key set there; the row *source* is still a table, and 「这张表的行从哪来」 asks about the second one. (These three shapes used to publish `[]`, which on a real corpus left most statements with no answer at all.) It changes no role value -- an aggregated source table keeps `role_in_task: aggregate_source` -- and the per-table marker for the same path is `inputs[].driving` (next row). `structural_summary` therefore opens by shape: a projection writes 「行来源 <table>（经 <scope> → <scope> 两次 LATERAL VIEW 展开）；补充 <the other tables ROOT reads directly>」 (the sentence runs in data-flow order, the reverse of `via_scopes[]`), an aggregated shape writes 「按 <grain keys> 汇总，行来自 <table>（经 …）；补充 …」, an empty grouping set (`grain.basis` is `single_row`) writes 「全表汇总，行来自 …」, and a deduplicated shape writes 「按 <keys> 去重，行来自 …」. Past three keys only the first three are named, followed by 「等 N 列」 (the whole list stays in `output_shape.grain.keys`). Where no driving path resolves, the old 「ROOT 直接读取 …」 wording is still the fallback |
| `inputs[]` | `comment` (the table comment: the first value among `table_name_cn` → `table_desc` → `comment` → `table_comment`), `domain` / `project` / `owner` / `layer` (table-level metadata facts, always present and `null` when absent), `role_in_task` (the most specific one), `driving` (P3, present only when `true`), `roles` (all of them), `used_columns[].usages`, `metadata_complete`, `table_column_count` | Roles (R7): `driving`, `merge_source`, `aggregate_source`, `dedup_source`, `union_branch`, `filter_partner`, `enrich`, `rowset_only`. `driving` follows `task.driving_tables[]` (B2) wherever that path resolves: a table off the path cannot hold `driving`, which is how a RIGHT JOIN's left side falls back to `enrich`. `filter_partner` (B2) is the other side of an INNER / SEMI / ANTI JOIN on the driving path -- it adds columns *and* **drops** the driving rows it cannot match, and `enrich` denies the second half. `driving` covers more than the table ROOT reads directly: a physical table that is a **non-ROOT scope's own FROM item** (by the same `_scope_from_item` rule — an input that is only ever a JOIN's right side is not one) is `driving` too, as long as that scope sits on ROOT's driving path (a UNION contributes all its branches) or its output columns are what ROOT groups by. Every GROUP BY key coming from one table while that table is labelled `enrich` points the reader at a lookup. A MERGE is excluded (R2 cannot classify its shape, and its sources stay `merge_source`). `driving` (P3) is a **different** fact: not a role, but the per-table marker for 「this table is on `task.driving_tables[]`'s driving path」, published for every shape (an aggregated, deduplicated or MERGE statement included) and **present only when `true`** -- its absence means the table is not on the path, not that this view never asked. Read it, or `task.driving_tables[]`, to find the main table; do not read `role_in_task` for that. An aggregated source table is `role_in_task: aggregate_source` *and* `driving: true`, and both are true. Usages: usages: `filter`, `partition_filter`, `join_key`, `group_by`, `window_partition`, `window_order`, `output`. `used_columns[].term_meaning` (WI-2.12) is the corpus dictionary's **human-confirmed** meaning for that column NAME, `{text, status}`, published beside the column's own `comment` rather than replacing it, and absent as a whole key when nobody confirmed one |
| `output_shape` | `shape`, `grain`, `candidate_keys`, `unexposed_keys`, `key_evidence`, `key_confidence`, `partition_columns`, `fan_out_risks[]` | Shapes (R2): `aggregated`, `deduplicated`, `union_merge`, `enriched_projection`, `filtered_projection`, `unknown`; `grain.basis` (R3): `group_by`, `distinct`, `window_partition`, `driving_table_rows`, `single_row`, `unknown` -- `single_row` (B10) is an aggregate over an **empty grouping set** (`SELECT COUNT(1) … FROM t`, no GROUP BY clause anywhere in the statement): the whole output is one row, so `grain.keys` is empty while `key_confidence` is always `proven` (an empty key set is trivially unique) and `candidate_keys` is empty. A UNION ALL of several such aggregates is **not** one row, and the union blocker on the grain walk keeps answering `unknown`; `grain.via_scopes`: the scope ids the recursive walk was pierced **through** (ROOT excluded, and the terminating layer excluded), empty when ROOT reads the answer directly; `grain.candidate` (B3) appears only where `basis = unknown`, the driving path really does carry a LATERAL VIEW expansion, and **the grain one layer below that expansion is itself decided**; it reads `{keys[], row_source, basis: "candidate", confidence: "hypothesis", reason, evidence[]}`, where `keys[]` is the pre-expansion grain's keys plus the columns each explode adds, `row_source` names the table only when the pre-expansion basis is `driving_table_rows` (which has no keys of its own to list) and is `null` otherwise, and `evidence[]` is the scopes carrying the LATERAL VIEWs. `grain.basis` **stays `unknown`** and neither `candidate_keys` nor `key_confidence` is affected by it -- it is a row shape the structure suggests, not one it proves. rendered as "注释未知", "comment unknown") — it is never translated, paraphrased, or guessed from
the column name. And when a join's extra condition tests a generated column, that column's upstream
fields go into `rules[].extra_condition_fields` (each flagged `via_generated_column: true`) rather
than `fields[]` — listing them as join keys would claim that `event_time` is one, which it is not.

### Corpus table cards: `describe --tables`

With a [`tables.json`](tables-doc.md) supplied, the profile gains three more things, **all
matched on the normalized table name**:

- `inputs[].card`: what the table's **producing task** proved — `produced_by_task`,
  `grain_text` (one structural sentence for "what one row represents"), `candidate_keys`,
  `key_confidence`, `comment`, `refresh`; `null` when no task in the corpus writes it.
- `task.downstream_consumers[]`: who reads this statement's target table, each entry giving
  `task` / `role_in_task` / `columns`; this statement itself is not counted.
- `confidence.metadata_coverage.table_cards`: the three counts `inputs_with_card` /
  `inputs_total` / `consumers`, saying how much of the input side a card could answer.

Without `--tables` those three keys **do not appear at all**, and `semantic.json` /
`semantic.md` are byte-identical to what they were before table cards existed — "no corpus
was supplied" and "the corpus proves nobody writes it" are different answers and never
render alike.

### Corpus concept layer: `describe --ontology`

With an [`ontology.json`](ontology-doc.md) supplied (**`ontology-json/2` only**; an older
document is refused with an error naming both `doc_format`s — `/1`'s `relations[]` meant
the table-level evidence, and reading it as `/2` would take that for the concept
relations), the profile gains five more things, **all matched on the normalized table
name**, and every one of them merely restates what the ontology already published: this
view adds no concept judgement of its own.

- `task.concepts[]`: the concept each table this statement reads or writes belongs to,
  each entry `{concept, name, kind, role, membership_basis, table, direction}` with
  `direction` one of `read` / `write`; **deduplicated by concept**, and a concept both
  read and written is published once, as the **write** ("this task produces a
  representation of the customer" is the stronger of the two facts, and the read is still
  visible on its own `inputs[]` entry), keeping the place its first mention earned.
- `task.output_concept`: the concept the target table represents and its role in it,
  `{concept, name, kind, role}`; `null` when the ontology does not model that table.
- `inputs[].concept`: the input table's **identity** concept (the same four keys) — what it
  **is**, never what it happens to point at: a member whose `membership_basis` is
  `reference` is never read as an identity. `null` when the ontology does not model it.
- `fields[].concept_attribute`: where the target column's physical source column (the
  first entry of `sources[]` the concept layer can place) sits in the concept layer,
  `{concept, name, attribute}`; where that column **is** the concept's identity key,
  `is_concept_key: true` is published alongside it (the key is asked first, the attribute
  second). A column with no physical source (`count(1)`, a constant) carries neither key.
- `output_shape.grain.concept_text`: the grain phrased as 「一行 = 一个客户 × 日期」. Three
  rules keep it a *reading* of the grain rather than a claim about one: it is published only
  where the layer placed **at least half** the grain keys (one key of four is not another
  way of saying the grain, it is a quarter of one); each business term is named **once** and
  the list is capped at 6 terms (`CONCEPT_GRAIN_TERM_LIMIT`) — a warehouse keying three
  tables by the same id used to produce 「… × 投放单元id × 投放单元id × 投放单元id」, which
  says one thing three times and buries the line; and a concept counts as one term
  **together with its own id column** (where one key is `concept:unit`'s identity and
  another is some other table's copy of the same `unit` stem, 「一个投放单元 × 投放单元id」
  is one thing said twice, and only the first is the concept). **Whenever it does not name
  every grain key** — one it could not place, two folded onto one term, or the cap — the
  sentence ends in 「等 N 列」 with N the real number of keys: that count is exactly what
  the folding costs the reader, so it is the one thing the sentence may not leave out, and
  the full list stays in `grain.keys[]`. An attribute is named by its own comment, falling
  back to its folded stem, and never by a word this view invented for it.

**A provisional concept (M1) carries `provisional: true` wherever it appears** above, and
only when true: a table published as a concept because nothing else placed it is a question
put to the review round, not an assertion about the business, and the reader has to be able
to tell the two apart at a glance.

`semantic.md` gains three things to match: section 1 gains a line 「- 涉及概念：客户（实体，
写入：汇总）、消息发送（事件，汇总读取）」 (and says 「本语料的概念层未覆盖本语句涉及的表」 where
the layer reaches none of this statement's tables, which is a different answer from the whole
line being absent without `--ontology`); section 2's grain line uses `concept_text` when there
is one (the `依据…`, `basis=…` and physical-source parts are unchanged); and section 5's
「完整字段清单」 gains a 「所属概念」 column wherever **at least one** column was placed
(`客户·cust_name`, or `客户·键` where the column is the identity key, `—` otherwise, with a
`（暂定）` suffix for a provisional concept).

Without `--ontology` those five keys **do not appear at all**, and `semantic.json` /
`semantic.md` are byte-identical to what they were before the concept layer existed.

### Confirmed write-backs: `describe --metadata-patch`

With a [`metadata-patch/1`](input-formats.md) file supplied, the view gains four more things,
all answering one question — **did the warehouse's metadata say this, or did a person**:

- `inputs[].comment_source`: `metadata` / `patch`; absent when the input table has **no**
  table comment at all (a sourced empty comment answers a question the document cannot);
- `fields[].target_comment_source`: the same two values, likewise only when the field has a
  target comment;
- `confidence.metadata_coverage.patch`: `{tables, columns}`, how many tables and columns in
  this statement the patch wrote; absent when no patch entry matched;
- `confidence.confirmations`: `{values_confirmed, rule_values_confirmed, terms_confirmed,
  columns_patched, tables_patched}`, **always present** — all zeros is a fact, and "nobody
  has confirmed anything about this task yet" is exactly the state the write-back loop
  exists to change. The first three counts are filled by `--glossary` (field value
  meanings, rule value meanings, column terms), the last two by the patch.
  `rule_values_confirmed` (WI-2.12) is counted apart from `values_confirmed` rather than
  folded into it: the same code written on an output column and written in a `WHERE` is a
  question a reader asks in two places, and a warehouse keeps most of its codes in the
  second one.

In `semantic.md` a patched comment carries the suffix `（人工确认）` after its text — once in
section 3's input table under 表注释, once on the `- 目标注释：` line of section 5's field
subsection. The trailing `元数据事实` tag vouches only for the comment existing; who claims it
is written inside the comment.

`parse --metadata-patch` and `describe --metadata-patch` go through the same function, so the
two paths produce a byte-identical `semantic.json`, `lineage_digest` included. Without a patch
the first three keys do not appear. How a business owner's answers become that patch file is
documented under "the write-back loop" in [the term and value dictionary](glossary-doc.md).

## The seven sections of `semantic.md` and their `--sections` names

| Section | `--sections` name | Content | Fact source |
| --- | --- | --- | --- |
| 1. 任务概览 (Overview) | overview | Target table and its comment, statement kind and partitioning, which metadata described the target, one 「本实例取数日」 line (present only when `task.instance_dates` is non-empty, worded as this instance's day that the scheduler replaces on every run, with 「（相差 N 天）」 appended when it holds more than one day), the one-line structural summary, one 「涉及概念」 line (only under `describe --ontology`), and the input-table table (comment, role, used/total columns, metadata completeness, reading scopes), one task-metadata line (project / owner / schedule cycle / schedule expression / expect date / description, with 「上游任务 N 个」 and 「下游任务 N 个」 appended per B4 — counts only, the names being in `task.meta`; a slot the metadata did not supply is left out, and the whole line disappears when none was supplied), the SQL header-comment blockquote (one `> ` line per comment, verbatim, under the heading 「SQL 头部注释（原文，作者说法，非 SQL 事实）」; the whole block is absent when there are none) | `task`, `inputs` |
| 2. 输出表形态与粒度 (Output shape and grain) | shape | Shape, the grain's logical keys and basis (with the pierce path and the physical sources behind them), keys or candidate keys as **target column names** (worded by `key_confidence`), then one 「- 说明：`<scope>` 的关联放大发生在分组之前，不影响输出键唯一性」 line under it per B12 note (read off `output_shape.key_evidence[]`; absent when there is none, and the other notes in that list do not render here), partition columns, per-JOIN fan-out risk along the grain path; the JOINs whose `path` is `argument` are listed apart, under a 「影响指标取值的关联：」 heading — they change the numbers, not the row count; a pinned grain key reads as `ROOT.dt（钉死为 '20260815'）` on the grain line, and a `grain.basis = single_row` writes 「一行 = 全表汇总」 there with 「输出只有一行，无需键即可唯一标识」 on the key line; where `grain.concept_text` exists (only under `describe --ontology`) the key half of the grain line is rewritten as 「一行 = 一个客户 × 日期」, leaving `依据…`, `basis=…` and the physical sources as they were; where `grain.candidate` exists the grain line carries on from 「未能判定」 with 「；候选：一行 = `<table>` 的一行 × `<exploded column>`（<reason>）[推断]」 — `[推断]` is the profile writer's own marker for a guess, and it is copied along with the sentence | `output_shape` |
| 3. 加工链路 (Processing chain) | stages | Stage by stage in topological order: role, direct inputs / directly read physical tables / upstream physical tables, action lines, output columns (an action line that has a comment ends in `（注释：…；SQL注释）`; WI-2.12: a restated filter / HAVING / join ends in `（取值：'01'＝人工队列；…）` before that, listing only the codes the dictionary has answered and writing 「等 N 个，见规则表」 past three) | `stages` |
| 4. 规则清单 (Rule list) | rules | Filters / HAVING / join conditions / CASE branches, one per row, with the involved fields' comments and an evidence id, plus an `SQL注释` column holding what the author wrote on that condition (`—` when there is none); WI-2.12: where the dictionary answered a code this statement writes, a 「取值含义」 column follows the condition (`'01'＝人工队列` confirmed, `'07'＝? 自动队列` candidate, `—` for a rule with no answer), and the whole column is absent when nothing was answered | `rules` |
| 5. 字段语义 (Field semantics) | fields (sub-switch fields_table) | The compact "完整字段清单" (full field list) table comes **first** (`#` / field / one-sentence meaning / structural role / 口径 / trace, plus a 「所属概念」 column where one is due, see below, where 口径 compresses the aggregation call and the time range into one cell and a non-metric field reads `—`), **then** one `###` subsection per field whose first line is `- 语义：<summary>` (unlabelled). A metric field follows that with a fixed seven-line 口径 card (subject / time range / inclusion / aggregation / unit and type / nulls / refresh cadence; an empty slot states why, such as "未在聚合路径上发现日期过滤", instead of dropping its line; a date filter read from the argument path is marked "（参数来源侧）" at the end of its 时间范围 entry, and the 空值 line reads "参数来自 LEFT JOIN 右侧（<scope>），关联不上时为空" where the argument is the nullable one; the 更新频率 row reads "每日（cron …）" when `task.meta` supplies a schedule and "未知（任务元信息未提供）" otherwise), then a `- 注释：…（SQL注释）` line (the author's own words along this field's derivation chain; the whole line is absent when there are none), and then target comment, type, sources, structural role, step-by-step derivation, final expression and trace status; where values were observed, a `- 取值：` line follows the comment line (a confirmed meaning plainly, a candidate prefixed `? `, neither as 「待确认」, with a closure note appended when the whole column is closed); WI-2.12: where the target comment is empty and the dictionary holds a confirmed term, a `- 术语：<meaning>（人工确认）` line follows `- 目标注释：`, and the 「完整字段清单」 gains a 「术语」 column (`<meaning> ✓` where there is one, `—` elsewhere) that is absent when no field carries a term; N5: where `describe --ontology` placed at least one column in the concept layer, the 「完整字段清单」 gains a 「所属概念」 column right after the one-sentence meaning (`客户·cust_name`, `客户·键` for an identity key, `—` elsewhere, suffixed `（暂定）` for a provisional concept); the column is absent when nothing was placed | `fields` |
| 6. 可信度与边界 (Confidence and boundaries) | confidence | Metadata coverage, incompletely traced fields, AMBIGUOUS, fact gaps, warning counts, one target-column-binding line, and a count of the document's own structural inferences, closing with a "治理线索" (governance leads) subsection that renders **only the `severity = warn`** entries of `findings[]`, one per line (or "治理线索：无" when there are none), and counts the `info` ones in a single "信息项：N（见 semantic.json findings）" line (omitted when N is 0); when there are warnings the line points at the `warnings.md` that `scope-lineage render` writes (`describe` does not write it) | `confidence`, `diagnostics.json` |
| 7. 给 Agent 的说明 (Notes for the Agent) | agent | Three fixed lines: this document is a fact skeleton; the business profile is generated separately from the prompt; any Chinese meaning not tagged `元数据事实` is not a business definition | Fixed text |

- Section numbering is fixed: `--sections` only hides sections and **never renumbers** them, so
  "section 5" means the same thing in every rendered document.
- `fields_table` is not an eighth section but a **sub-switch** of section 5: passing it (instead of
  `fields`) keeps the "完整字段清单" table and drops the per-field subsections — exactly what a
  112-field task needs when a person reads it. Passing `fields_table` enables `fields`
  automatically; there is no need to pass both.

## Line grammar (semantic-md/1)

Machine readability comes from `semantic.json`; the markdown guarantees only the rules below.

### Front matter

A statement document's head is a **flat** YAML front matter block: one `key: value` per line, where
the value is always a JSON scalar (directly `json.loads`-able). It contains no timestamp and no
renderer version, so rendering the same input is byte-identical. The keys are fixed:

```yaml
---
doc_format: "semantic-md/1"
schema_version: "1.0"
task_name: "..."
target_table: "..."
stmt_kind: "..."
lineage_digest: "..."
---
```

`lineage_digest` comes from the same function mapping.md uses
(`scope_lineage.render.mapping_markdown.lineage_document_digest`: the SHA-256 prefix of key-sorted
compact JSON, 16 hex characters), so the mapping.md and semantic.md derived from one `lineage.json`
carry the same digest — which is how you confirm that two derived documents describe one snapshot.

A task document's head is not front matter: one `# 任务语义描述：<task_id>` line, one line reading
"共 N 条写入语句；最终产出表：…" ("N write statements; final produced tables: …"), then one
`## <statement_id>` section per write statement holding that statement's complete document (with
its own front matter).

### The tag suffix and evidence ids

Every line ends with its source tag, and all four tags share one grammar:

```
（<tag>[；证据 <id>[, <id>]]）
```

- `<tag>` is one of `SQL事实`, `元数据事实`, `SQL事实+元数据事实`, `结构推断`, `SQL注释`.
- `SQL注释` is the only label the document does **not** derive: the text it marks is the SQL author's own words, quoted verbatim. Content carrying it is **never placed in a code span** — a code span in this document means "a verbatim SQL identifier or expression", and free text put there would be read as a real identifier by both a person and the anti-fabrication check.
- After `证据` ("evidence") comes a comma-separated list of contract ids: `logic_block_id`,
  `mapping_chain_id`, `scope_id`, or a table name. When there is no id worth citing, the whole
  "；证据 …" part is omitted and the line ends in a bare `（<tag>）`.
- An action line carrying both `evidence` and `consumed_by` lists both ids — a window intent only
  holds because of a downstream `= 1` filter, so the evidence chain must be complete.
- Expressions always sit in code spans whose backtick fence grows past any backtick inside the SQL;
  a `|` inside a table cell is escaped as `\|`; and real newlines in rendered values are normalized
  to the literal `\n`, keeping "one fact per line".

### Uncertainty markers

The `⚠` prefix is used consistently, and nothing unprovable is written as a fact:

- section 2: `⚠ 有放大风险` (`risk`) / `⚠ 未知` (`unknown`), an unprovable grain reads
  `⚠ 粒度：未能判定（basis=unknown）`, and a key set that holds but was never written out
  reads `⚠ 键：…未输出到目标表；目标表列 … 不能唯一标识一行（key_confidence=proven_unexposed）`;
- section 1, the input table's metadata column: `⚠ 不完整` / `⚠ 未知`;
- section 5: `⚠ 粒度=unknown` on a step line, `⚠ 追溯：不完整——<reason>`, and `⚠` in the full field
  list's trace column;
- section 6: `⚠ 追溯不完整字段`, `⚠ AMBIGUOUS 字段`, `⚠ 无 diagnostics 文档`, and, when the target
  column comments are unavailable, `⚠ 不可用——字段语义退化为来源注释加加工复述` ("unavailable —
  field semantics degrade to source comments plus a restatement of the transformation").

### Folding and truncation

A long document folds, but **folding never drops an id**:

| Rule | Threshold | Behavior |
| --- | --- | --- |
| Section 3 stage folding | more than 12 stages | stages sharing a `pattern_signature` merge into one table (listing **every** member's topological number and `scope_id`, plus role, direct inputs, action summary and output column count, under a heading reading "阶段 2、5、6 等 3 个同模式阶段") and the first of them is expanded as a `####` subsection representative; ROOT is always expanded on its own |
| Section 3's source-boundary line | always | `上游物理表（来源边界）` is dropped where it equals the stage's own direct inputs or the line the previous stage already printed (the JSON is untouched) |
| Section 3 `derive` actions | more than 8 in one scope | folded to "派生 N 列：a、b、c…（前 3 条展开）"; the remaining action lines are not printed one by one |
| Section 4 same-shaped rule families | 3 or more rules of the same `kind` / `scope` that are identical once numeric literals are replaced by `N` | merged into one row, "rule:021–032（12 条）：`<template>`（N 取 9…20）"; where a rule carries several digit runs the renderer does not guess which one is `N` and defers to `semantic.json rules[]` |
| Section 5 runs of carrying steps | 2 or more | consecutive `direct_projection` / single-branch `union` steps fold into "第 k–m 步：直接透传（经 scopeA → scopeB → …）"; a run that sits inside UNION branches reads "各分支直接透传（经 A、B）" with **no arrow** — the branches are alternatives, not a sequence |
| A folded group's action summary | 120 characters | the rest is truncated to `…`; the full actions stay in the representative stage and in `semantic.json` |
| A stage's output columns | 20 columns | beyond that only the count and the first 20 names are printed |
| CASE branch restatement | 6 branches | beyond that it folds to "N 个分支，前 3 个：…" ("N branches, first 3: …"); the full branches stay in `rules[].branches[]` |
| The structural-inference inventory | always | section 6 only counts them grouped by `semantic.json` path; the full list stays in `confidence.inferred_items` |

`semantic.json` **never folds**: anything the markdown folded or truncated is available in full in
the JSON.

### Chunk self-containment

In section 5 each field gets one `###` subsection whose title carries the full identity from
`column_label` (`### 字段 <target table>.<field>`); a `directory:` target is named as a directory
and an unbound target column does not compose `<target table>.<field>` — the naming rules are the
same as mapping.md's, so after chunking on `###` any single subsection still locates itself when
retrieved alone. In section 3 each stage is likewise one `###` subsection whose title carries the
`scope_id` and the role.

## An excerpt from a real run of the examples

The following is the **verbatim output** of section 2 of `semantic.md` for
`examples/tasks/customer/customer_profile_daily.json` after `parse` → `describe` (it is not a
hand-written sample):

```markdown
## 2. 输出表形态与粒度

- 形态：关联补充型投影（enriched_projection）（结构推断；证据 logic:ROOT:join:001, logic:ROOT:join:002）
- 粒度：一行对应 `ods.customer_base` 的一行（依据主表行，basis=driving_table_rows）（结构推断；证据 ods.customer_base）
- 候选键：目标表列 `customer_id`——仅为候选，输入中无主键声明（分区内）（key_confidence=candidate）（结构推断）
- 分区列：`dt`；分区列不计入候选键（元数据事实）
- 行数放大风险：
  - LEFT_OUTER JOIN `cte:latest_status`：安全（safe）——右侧 row_number 按 customer_id 分区并以 = 1 过滤（logic:ROOT:join:001）（结构推断；证据 logic:ROOT:join:001）
  - LEFT_OUTER JOIN `cte:order_summary`：安全（safe）——右侧按 dwd.order_detail.customer_id GROUP BY，键集被连接键覆盖（结构推断；证据 logic:ROOT:join:002）
```

How to read it: both JOINs are judged `safe` because the right side is provably unique per join key
(one by `row_number() = 1`, one by a `GROUP BY` key set covered by the join keys). Only those
provable forms are granted; when the right side is a physical table the answer is always `unknown`
— a physical table declares no primary key, so there is no fact to stand on.

JOINs on a metric's argument path are listed under their own heading, because they need a
different action: a fan-out on the grain path adds **rows**, while one on the argument path adds
**rows that get summed** — the output row count is untouched and the number is too large.

```markdown
- 行数放大风险：
  - LEFT_OUTER JOIN `subq:v`：⚠ 有放大风险（risk）——右侧未被证明按连接键唯一（结构推断；证据 logic:ROOT:join:001）
- 影响指标取值的关联：
  - `subq:v` 中的 INNER JOIN `subq:g`：⚠ 有放大风险（risk）——右侧未被证明按连接键唯一（结构推断；证据 logic:subq:v:join:001）
```

## Determinism and golden baselines

Describing the same pair of input documents twice is byte-identical: fields are sorted by
`target_column_ordinal` (falling back to `output_ordinal`, then to the original order), stages are
in topological order, rules are numbered `rule:001`… in scope-topological order and then by
`logic_block_id` within a scope, and input tables are sorted by name. There is no timestamp, no
renderer version, no LLM call, no network request, and no new dependency. The property is locked by
the golden baseline tests (`tests/core/fixtures/lineage_contract/<case>/semantic.json` and
`semantic.md`), plus a property test asserting that every table and column name appearing in the
document exists in the source `lineage.json` — the anti-fabrication guard.

## Division of labour with mapping.md

Both documents are rendered from the same contract, so they cannot drift apart, but they take
different views:

- [mapping.md](mapping-doc.md) gives the technical detail scope by scope: the field mapping table,
  the step-by-step chains, the logic summary, and the mermaid graph. Read it for "where exactly did
  this column come from, and which scopes did it pass through".
- semantic.md restates the actions in topological order and attaches the comments: output shape and
  grain, stage actions, the rule list, field semantics. Read it for "what does this task do, what
  does one output row represent, what does this field mean".
- Sections 3 and 4 overlap in facts with mapping.md's section 6 — that is two views of the same
  `logic_blocks`, not two sources of truth.
- For choosing the layer, see [statement level or task level?](contract-selection.md); for the
  artifact structure, see the [`lineage.json` output contract](lineage-json.md) and the
  [`diagnostics.json` output contract](diagnostics-json.md).
